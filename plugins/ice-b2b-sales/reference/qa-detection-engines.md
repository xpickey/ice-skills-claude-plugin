## 1. D5 สำนวน AI และ D5.TL ศัพท์แปล

**ลำดับการตรวจ:** (1) อ่านผล `python3 ~/.claude/agents/_lib/thai_style_check.py <ไฟล์> --register business|academic` ที่ระบบรันให้หลังสร้างไฟล์ ถ้าไม่มีให้รันเอง — ทุกรายการ "ต้องแก้" ถือเป็นประเด็น D5 ทันที ไม่ต้องอ่านซ้ำ (2) เทียบศัพท์กับ `_build/glossary.md` ในโฟลเดอร์งาน (3) จึงโหลด skill `thesis-ai-det-col` เข้ามาตรง ๆ (ไม่เรียก agent) เพื่ออ่านสิ่งที่เครื่องวัดไม่ได้: สำนวนติดปาก AI ภาษาไทย ("เป็นที่ทราบกันดี" "ปฏิเสธไม่ได้ว่า") คำ AI ภาษาอังกฤษ (delve · leverage · robust · seamless) รูปแบบ 24 ชนิดตามคลังของ skill ชั้นสถิติ (จังหวะประโยค burstiness) และความหนาแน่นของคำเสี่ยง · คำตัดสิน: คะแนน AI เกินเกณฑ์ในงานถึงลูกค้า = BLOCK

**การเทียบอภิธานศัพท์:** `_build/glossary.md` คือศัพท์ที่ผู้สร้างเลือกพร้อมแหล่งที่มา (กติกาข้อ 3 ของ skill ice-writing-register) · ศัพท์ในเอกสารที่ต่างจากอภิธานโดยไม่มีเหตุผล หรือคำแปลไทยที่ไม่มีในอภิธานและไม่พบในเอกสารลูกค้า = ประเด็นถ้อยคำ (D8) พร้อมเสนอคำที่ถูกต้อง · ไม่มีไฟล์อภิธาน = บันทึกประเด็นย่อย (minor) ว่าผู้สร้างข้ามขั้นสกัดศัพท์

**D5.TL ศัพท์แปลและชื่อ feature ของ product — ชี้เป้าอย่างเดียว 3 เป้า:**
1. คำแปลไทยที่ทึบกว่าคำอังกฤษเดิม → ชี้พร้อมคู่เทียบ
2. ชื่อ feature ของ product ที่สื่อหน้าที่ผิด → จัดประเภท `term-misname` แล้วให้ผู้เรียกส่ง ③ ยืนยัน (อริสไม่ยืนยันชื่อ feature เอง)
3. สำนวนวิชาการหลุดเข้าเอกสารธุรกิจ → จัดประเภท `term-localization`

ข้อที่ห้ามชี้ผิด: ศัพท์บัญชีไทยมาตรฐาน (บัญชีแยกประเภท งบทดลอง ค่าเสื่อม ผังบัญชี การกลับรายการ กระทบยอด) · ป้ายจัดประเภท 4 คำ Configure/Customization/Integration/Workaround ที่คงสองภาษา · คำที่ผูกคำอังกฤษกำกับครั้งแรกถูกแล้ว
คำตัดสิน: แจ้งเตือนและส่งต่อ ไม่ระงับอัตโนมัติ — ยกเว้นชื่อ feature ในงานถึงลูกค้าที่อริสมั่นใจสูง (confidence high จากหลักฐานเทียบในมือ) ให้ตั้งระดับ critical ไว้ก่อนเพื่อกันงานหลุดถึงลูกค้า คำยืนยันสุดท้ายยังเป็นของ ③ ผ่านผู้เรียก

## 2. D7 ฟอนต์และการจัดหน้า — สาย PPTX · สาย HTML · สาย PDF วิชาการ

**หลักของมิตินี้:** ผลตรวจอัตโนมัติสี่ตัวมาก่อนคนเสมอ — `audit_fonts.py` (ชื่อฟอนต์มีจริง · ไม่อยู่ในรายการต้องห้าม · ตรงราง private/govt · ช่องฟอนต์ไทยครบ) · `audit_layout.py` (ล้นขอบ · ซ้อนกัน · เกินงบคำ · หน้าไม่มีภาพ · คำว่าวัตถุประสงค์หลุดขึ้นสไลด์) · `validate_pptx_fonts.py` (ฝังฟอนต์จริง) · `validate_pptx_structure.py` (โครงสร้างไฟล์ที่ PowerPoint จะขึ้นกล่อง Repair) — สี่ตัวนี้เป็นด่านของผู้สร้างก่อนส่ง อริสอ่านผลแล้วตรวจเฉพาะสิ่งที่เครื่องตรวจไม่ได้ ตามรายการด้านล่าง · งานถึงลูกค้าที่พบการฝ่าฝืน = BLOCK · งานภายใน = แจ้งเตือน · ด่านฟอนต์มี 3 ชั้น: ผู้สร้างตรวจเอง → อริส (มิตินี้) → ผู้เรียกด่านสุดท้าย

**สาย PPTX — สิ่งที่อริสตรวจด้วยตาและเครื่องมือเสริม:**
- **ขนาดตามสายตา (D7.3):** งานไทยล้วน เนื้อความอย่างน้อย 18pt หัวเรื่องอย่างน้อย 24pt · ฟอนต์เดียวครอบสองภาษาต้องใช้ขนาดเท่ากัน (กฎเก่า "ไทยใหญ่กว่า 1–2pt" ยกเลิกแล้วเพราะไม่มีต้นทางจริง) · จับคู่สองตระกูลให้ชดเชยด้วยอัตราส่วนความสูงตัวอักษรตาม ice-doc-builder §1 D3
- **ภาพจริงบนหน้า (D7.4):** ผล `audit_layout` และ `validate_pptx_fonts` ต้องผ่านแล้วตั้งแต่ E0 · อริสเปิด render สด (ไฟล์ `qa-render-evidence.md`) ดูว่าสิ่งที่เครื่องนับไม่ได้ เช่น ข้อความชนขอบภาพ ตัวอักษรถูกย่อจนอ่านยาก แถวตารางขาด เกิดจริงหรือไม่ และเปิดใน PowerPoint จริงว่าไม่ขึ้นกล่อง Repair
- **ที่มาของข้อยกเว้นฟอนต์ (D7.6b/D7.6d):** ก่อนชี้ว่าฟอนต์ผิดนโยบาย ให้ถามสองข้อ — ไฟล์นี้ทีมสร้างหรือลูกค้าส่งมา (ไฟล์รับมาตรวจด้วย `--allow-font`) และ TOR ระบุฟอนต์หรือไม่ (TOR ชนะนโยบายเสมอ) · งานต่อยอดจากแม่แบบหรือ deck เก่า การสืบทอดฟอนต์ไม่ผ่านอัตโนมัติ ผ่านได้เมื่อ spec หรือ QA log มี `font_override_reason` ที่อ้างคำสั่ง user ได้จริง · ตรวจที่มาของ `--allow-font` ทุกครั้ง เพราะผู้สร้างอนุมัติให้ตัวเองไม่นับ · คำสั่งตรวจซ้ำเมื่อสงสัย: `python3 ~/.claude/agents/_lib/audit_fonts.py [--rail private|govt] [--allow-font ชื่อ] <ไฟล์>` (รองรับ .xlsx .pptx .docx .html .pdf)
- **ตัดบรรทัดกลางคำไทย (D7.7 — แจ้งเตือน):** ภาษาไทยไม่มีช่องว่างระหว่างคำ โปรแกรมจึงตัดกลางคำได้ · ตรวจด้วย `python3 ~/.claude/agents/_lib/thai_wordbreak.py --audit <ไฟล์> [--col C] [--all]` · เจอรอยตัดหรือความกว้างคอลัมน์ผิดแม้จุดเดียว ให้วัดและรายงานทั้งตารางในรอบเดียว: ความกว้างขั้นต่ำที่ต้องการของทุกคอลัมน์ (คำกว้างสุด + หัวตารางตัวหนา + ขอบเซลล์) เทียบความกว้างจริง เป็นตารางแนบใน finding — เพราะการรายงานเฉพาะคอลัมน์ที่พังทำให้ผู้แก้หักความกว้างจากคอลัมน์ข้างเคียงแล้วปัญหาย้ายจุด (เคสจริง TQR Work Order วน 5 รอบ) · ความรุนแรงตามความถี่และตำแหน่ง (หัวตารางและหน้าปกสำคัญกว่า) · เสนอทางแก้ตามลำดับ: ขยายคอลัมน์หรือกล่อง → ปรับข้อความ → ZWSP เป็นทางสุดท้าย และห้ามใช้ ZWSP กับเอกสาร TOR ที่ถูกนำไปทำดัชนีค้นหา
- **อักขระไทยผิดรูป (D7.8 — แจ้งเตือน):** สระซ้ำหรือเรียงผิดที่ตามองไม่เห็น เช่น "เเละ" (สระเอสองตัว) แทน "และ" ทำให้การค้นหาและเทียบเอกสารพลาดเงียบ ๆ · ตรวจด้วย pythainlp normalize เทียบข้อความก่อนและหลัง

**สาย HTML (งานนำเสนอบนเว็บ — ตรวจด้วยการเปิด browser จริง ไม่ใช่ LibreOffice):** ขนาดจอ 16:9 คงที่ · เนื้อไม่ล้นที่ 1920×1080 · ความต่างสีผ่านเกณฑ์อ่าน (อย่างน้อย 4.5:1 งานฉายจอเป้าหมาย 7:1) · แสดงผลได้ที่ 1280×720 และบนโทรศัพท์ · ฟอนต์ไทยมาก่อนละตินใน font stack · รองรับผู้ใช้ที่ปิดการเคลื่อนไหว · ไม่มีอักษรลูกศรในเนื้อความ · ตัดคำไทยด้วย CSS (`lang="th"` + `word-break:normal` — ห้าม `break-all` เพราะผ่ากลางคำทุกที่) ไม่ใช้ ZWSP · เปิด browser จริงดูว่าไม่มีคำถูกผ่ากลาง · การฝังฟอนต์แบบ PPTX ทำไม่ได้ ใช้ CDN พร้อม fallback ไม่ถือว่าผิด

**สาย PDF วิชาการ:** ใช้ในโหมดตรวจงานวิชาการ (`qa-academic-mode.md`) ตามเกณฑ์ของมาตรฐานเอกสารที่หาได้ในขั้นที่ 0 ของโหมดนั้น

## 3. D8 ถ้อยคำ และ D8.C ข้อความประกอบในเอกสาร

**D8:** ตรวจถ้อยคำตามกติกา 8 ข้อของ skill ice-writing-register ที่อยู่ในบริบทอยู่แล้ว — ภาษาธุรกิจที่คนไม่มีพื้นเทคนิคเข้าใจ · ไม่ย่อคำ ไม่ใช้คำย่อที่ไม่สะกดเต็มครั้งแรก · ไม่มีรหัสภายในหรือคำแปลประหลาดหลุดในเอกสาร · น้ำเสียงทางการ · สัดส่วนถ้อยคำเชิงบวกตามกติกา Positive Wording ของ skill ice-b2b-enterprise-sale §6A (บ้านเดียวของสัดส่วนนั้น) · คำตัดสิน: งานถึงลูกค้าที่ฝ่าฝืน = BLOCK

**D8.C การสแกนข้อความประกอบ** (คอลัมน์คำอธิบาย หมายเหตุ เหตุผล ทุกคอลัมน์ในเอกสาร) — 5 ตัวจับ:
1. เศษวลีสั้นกว่า 60 อักษรที่ควรเป็นประโยคอธิบาย
2. เครื่องหมาย + หรือ → ที่ใช้เชื่อมความในเนื้อความ
3. รหัสที่ประดิษฐ์ขึ้น (ตัวอักษรตามด้วยตัวเลข เช่น [E1]) โดยไม่มีตารางนิยามในเอกสาร
4. สำนวนขึ้นต้นซ้ำเกินราวหนึ่งในสี่ของชุดรายการที่เขียนขนานกัน
5. รหัสรายการ (รูปแบบ XX-000 เช่น BR-003) ที่ตามด้วยป้ายสั้นกว่า 20 อักษร หรือไม่มีคำอธิบายในบรรทัดหรือตารางนิยาม รวมถึงชื่อที่แปลตรงตัวประหลาด

เจอข้อใด = บันทึกเป็นข้อบกพร่องระดับ major สำหรับงานถึงลูกค้า · งานภายใน = minor (ที่มา: เคสจริงคอลัมน์คำอธิบายแบบโทรเลขพร้อมรหัส [E1] และ "BR-003 ตรึงประชากร" หลุดถึงลูกค้า)

## 5. D9 การเทียบข้อกำหนดรายข้อ — ชี้ผลอย่างเดียว

ทำ: เทียบงานกับเอกสารข้อกำหนด (TOR/RFP ที่ซองคำสั่งระบุในช่อง `requirement_source`) ทีละข้อ ให้ผล ตรง / บางส่วน / ขาด / เกิน / เบี่ยงเบน พร้อมเลขหน้าของงาน · เทียบได้หลายมิติ: กับ TOR กับรุ่นก่อน กับคู่แข่ง และกับความเห็นลูกค้า
ไม่ทำ: ไม่บอกว่าต้องแก้อะไร ไม่ตัดสินว่าความเบี่ยงเบนผิดหรือตั้งใจ — คืนผู้เรียกตัดสินทั้งหมด · ใช้เฉพาะ `qa_mode = compliance` หรือ `both`

## 6. เครื่องตรวจภาษาบาลี — D3 + D2

**เปิดใช้เมื่อ** งานมีสัญญาณอย่างใดอย่างหนึ่ง: อักษรไทยที่มีพินทุ ฺ หรือนิคหิต ํ · โรมันที่มี IAST · การอ้างพระไตรปิฎก พุทธพจน์ หรือชื่อหลักธรรมบาลี → โหลด skill `pali-language` (`~/.claude/skills/pali-language/`) ทันทีโดยไม่ต้องให้ผู้เรียกสั่ง (คำสั่ง user 2026.09.03) · การอ่านเอกสารบาลีจาก PDF ให้ใช้ขั้นตอน dual-source ในไฟล์ `references/09-document-ingestion.md` ของ skill นั้น (text layer สำหรับคำบาลีและโรมัน IAST · OCR สำหรับร้อยแก้วไทย) เพราะตัวอ่านเอกสารทั่วไปจะรายงานว่าข้อความไทยเสียหายเป็นเรื่องปกติของเอกสารบาลี
