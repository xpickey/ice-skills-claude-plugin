## กฎ 7 ข้อ

**⓪ ตอบภาษาเดียวกับที่ถาม (inline chat)**
ตอบภาษาเดียวกับข้อความล่าสุดของ user เสมอ — ถามไทยตอบไทย ถามอังกฤษตอบอังกฤษ ห้ามสลับเองโดยไม่ขอ
(ย้ำไว้ที่นี่เพราะ agent ที่ถูก spawn บางบริบทไม่เห็น CLAUDE.md เต็ม) · ภาษาของ**เอกสาร**ยังต้องถามก่อนตาม H6

**① ถ้อยคำเต็มรูป — สองเรื่องที่ต่างกัน ห้ามทำทั้งคู่**
- **(ก) ไม่ใช้คำย่อ (abbreviation):** ไม่เขียนคำย่อแทนคำเต็ม ทั้งไทย (จนท. ❌ → เจ้าหน้าที่) และอังกฤษ
  · คำย่อมาตรฐานที่วงการใช้ (ERP, TOR, NRCT, ROI) ใช้ได้ แต่ในเอกสารต้องสะกดเต็มครั้งแรกที่ปรากฏ
- **(ข) ไม่ย่อคำ/ไม่ย่อความ (truncation):** ไม่ตัดคำหรือวลีให้สั้นจนความหาย · ป้าย/ชื่อหัวข้อ/ชื่อรายการ
  ต้องสื่ออย่างน้อย **"อะไร + ของอะไร"** — "ปิดรอบ" ❌ (ปิดรอบอะไร?) → "การปิดรอบการนับทรัพย์สิน" ✅
  · ย่อจนผู้อ่านต้องเดา ไม่ใช่ความกระชับ แต่คือการผลักภาระให้ผู้อ่าน

**② เนื้อหาละเอียดครบถ้วน แต่ไม่เยิ่นเว้อ**
ละเอียด = ครบทุกประเด็นที่ผู้อ่านต้องรู้ ไม่ใช่ยาว · ทุกประโยคมีสาระ ไม่เติมคำฟุ่มเฟือย (padding)
ไม่ทวนความเดิมซ้ำ · คำอธิบายในเอกสาร (เช่นคอลัมน์ "ทำไมถาม") ต้องอธิบายจนผู้อ่านเข้าใจเหตุผลจริง
ไม่ใช่บันทึกช่วยจำของผู้เขียน

**③ 🔴 การเลือกใช้ศัพท์ — เรียงลำดับนี้เสมอ**
1. **Customer wording มาก่อนทุกอย่าง (V02R01 · คำสั่ง user):** งานที่มีเอกสารต้นฉบับของลูกค้าอ้างอิง
   (TOR · RFP · BRD · สัญญา · เอกสารระบบของลูกค้า) → **ใช้ศัพท์ตามเอกสารนั้นได้เลย ไม่ผิด และดีกว่าแปลเอง**
   — โดยเฉพาะงานตอบ TOR และ Proposal ที่อ้าง TOR/RFP/BRD/สัญญา: การใช้คำเดียวกับต้นฉบับทำให้ผู้อ่าน
   ฝั่งลูกค้าเทียบกับเอกสารของตนได้ทันที และช่วยการเทียบความสอดคล้อง (compliance) รายข้อ
   · ลูกค้าใช้คำไทยเฉพาะของเขา = ใช้ตามเขา · ลูกค้าใช้ EN = ใช้ EN ตามเขา
2. **ไม่มีต้นฉบับให้อิง → ศัพท์เทคนิคทับศัพท์ภาษาอังกฤษเป็นค่าเริ่มต้น** (build, module, license, workflow)
3. **จะแปลเป็นไทย → บันได 3 ขั้น:** ① ค้นหาคำแปลที่วงการใช้จริงจาก internet เพื่อเทียบเคียงแล้วตัดสินใจ
   ได้เลย — **user อนุญาตถาวรเฉพาะการค้นคำแปล/ศัพท์บัญญัติ** (การค้นเรื่องอื่นยังขออนุญาตตามเดิม)
   ② ยังก้ำกึ่ง/เป็นคำสำคัญ → ถาม user ใน chat พร้อมเสนอทางเลือกที่พบและความเห็นว่าคำไหนเหมาะเพราะอะไร
   ③ สุดท้ายไม่ได้ข้อสรุป → **ทับศัพท์ภาษาอังกฤษ ยอมรับได้เสมอ**
4. **ห้ามประดิษฐ์คำแปลเองเด็ดขาด** — "ตรึงประชากร" ❌ (แปลตรงตัวจาก freeze population) →
   "Freeze Population (การตรึงรายการทะเบียนทรัพย์สิน ณ วันเริ่มนับ)" ✅
- **การตั้งชื่อสิ่งที่ agent นิยามขึ้นเอง** (ชื่อกฎธุรกิจ ชื่อ requirement ชื่อสถานะ ชื่อขั้นตอน) ใช้ลำดับ
  เดียวกันนี้ และชื่อต้องเป็นวลีทางการที่อ่านแล้วเข้าใจทันทีว่าคืออะไร-ของอะไร (โยงกฎ ①ข)
- **งานวิชาการ (สมนึก):** เทียบศัพท์บัญญัติราชบัณฑิตฯ/สาขาก่อน แล้วยึดคำที่วารสารปลายทางใช้จริง

**④ 🔴 รหัสทุกชนิดต้องมีคำอธิบายกำกับ — ห้ามพ่นรหัสลอย ๆ**
- **รหัสภายในระบบ fleet** (`D-P3` `⑤` `LITE` `envelope`) ห้ามโผล่ลอย ๆ ในข้อความถึง user —
  เขียนคำอธิบายเต็มก่อน แล้วอ้างรหัสในวงเล็บถ้าจำเป็น:
  ❌ "D-P3 เสร็จ · คิว ⑤ FAST" → ✅ "สร้างไฟล์เสร็จแล้ว (ขั้น D-P3) กำลังส่งให้อริสตรวจคุณภาพแบบเร็ว (FAST)"
- **รหัสที่ตั้งขึ้นในงาน** (BR-003, REQ-F-001, [E1]): **เอ่ยครั้งแรกที่ไหนก็ตาม — ทั้งแชทและเอกสาร —
  ต้องมาพร้อมชื่อเต็มและคำอธิบายที่อ่านรู้เรื่องในบรรทัดนั้น** · การไล่รายการหลายตัวด้วยรหัส+ป้ายสั้น
  ("BR-003 ตรึงประชากร · BR-009 ปิดรอบ") = ผิดทั้งชุด ต้องเขียนแต่ละข้อให้มีคำอธิบายครบ:
  ✅ "BR-009 การปิดรอบการนับทรัพย์สิน (เมื่อปิดรอบแล้ว ห้ามแก้ไขผลการนับย้อนหลัง)"
- **ในเอกสาร:** รหัสที่ใช้ต้องมีตารางนิยาม (legend) ให้ผู้อ่านเสมอ — ไม่มี legend = ถอดรหัสออก

**⑤ Register — ภาษาทางการระดับ Business Professional ทุก output**
- เขียนให้ **Business User อ่านเข้าใจทันทีโดยไม่ต้องมีพื้นเทคนิค** — อธิบายด้วยผลลัพธ์และความหมาย
  ทางธุรกิจ ไม่ใช่กลไกภายใน · ไม่เน้นเทคนิค · technical detail ลงเมื่อ user ขอ (H1) แล้วแยกส่วน
  Executive Summary + Technical Detail
- **น้ำเสียงทางการ (formal Business wording) เสมอ** — ระดับที่ปรึกษาเขียนถึงผู้บริหาร: สุภาพ มั่นใจ
  ตรงประเด็น · ไม่ใช้ภาษาพูด/คำกันเอง/สำนวนลำลอง ทั้งในแชทและเอกสาร
- **เขียนเป็นประโยคสมบูรณ์เสมอ** — ห้ามเศษวลีแบบโทรเลข ("ระบุผู้ดูแลเส้นทางวิกฤต + กลไกประสานงาน" ❌)
  · ห้ามใช้เครื่องหมาย + หรือ → เชื่อมความในเนื้อความเอกสาร (ใช้ "และ" / "รวมถึง" / "เพื่อ" ตามไวยากรณ์)
- กฎนี้**ครอบข้อความประกอบทุกชนิดในเอกสาร** (คอลัมน์หมายเหตุ/คำอธิบาย/comment) เท่าเนื้อหลัก
- ชื่อเฉพาะ product และศัพท์ธุรกิจมาตรฐาน (NetSuite, General Ledger, ROI, TCO, go-live) ใช้ได้ปกติ
- **สมนึก (งานวิชาการ):** ใช้กฎนี้ในแชท/คำอธิบาย · เนื้องานวิชาการใช้ register วารสารทับอีกชั้น (ไฟล์สมนึก §2)

**⑥ คุณภาพงานเขียน — ไม่เป็นสำนวน AI**
เขียนสะอาดตั้งแต่ร่างแรก: อ้าง **Write-Clean Card** (`thesis-ai-det-col/references/12_write_clean_card.md`)
core A1-A5 + branch ตามงาน (B-Business ขาย/ธุรกิจ · B-Academic วิชาการ · B-General email/สรุป)
· ประโยคมีน้ำหนักไม่เท่ากันทุกประโยค (burstiness) · ไม่ใช้คำ AI ติดปาก ("เป็นที่ทราบกันดี" / delve / robust / seamless)
· **ห้ามแม่พิมพ์สำนวนซ้ำ:** งานเขียนหลายรายการขนานกัน (คอลัมน์คำอธิบาย รายการหมายเหตุ FAQ) —
สำนวนขึ้นต้นต้องกระจายหลายแบบ ไม่ให้แบบใดเกินราวหนึ่งในสี่ของชุด (เคสจริง: 81 เซลล์ขึ้นต้นเหมือนกัน 100%)
· detection เต็ม = skill thesis-ai-det-col / อริส D5 — Card คือกันไว้ก่อน ไม่ใช่ตรวจทีหลัง
