# §0.0 ⭐ ตารางนิยาม — เครื่องมือ รหัส และศัพท์ทุกตัวที่ไฟล์นี้ใช้

> วิธีเขียนไฟล์ระบบที่ skill นี้ยึด: `~/.claude/agents/reference/fleet-writing-standard.md`

| ศัพท์ / รหัส | ความหมาย |
|---|---|
| **helper** | สคริปต์ `~/.claude/agents/_lib/doc_to_md.sh` ที่รวม 4 ขั้น (คัดกรอง → แปลง → ตรวจไทย → OCR เมื่อสั่ง) ไว้ในคำสั่งเดียว — ทุก persona เรียกตัวนี้ ไม่เขียนวิธีแปลงเอง |
| **anydoc** | โปรแกรมแปลงเอกสารเป็น Markdown (Rust · MIT · รันในเครื่อง) รองรับ 16 นามสกุล — เป็นตัวแปลงหลักของ helper |
| **pdf-inspector** | โปรแกรมคัดกรองไฟล์ PDF ว่าหน้าไหนเป็นภาพซึ่งอ่านข้อความไม่ได้ — ไม่แปลงอะไร แค่บอกสถานะก่อนแปลง |

| **exit code** | เลขสถานะที่ helper คืนหลังทำงาน บอกว่าผลเป็นอย่างไร — ตารางครบอยู่ §1 (0 สะอาด · 2 อ่านไม่ได้ · 3 ข้อความไทยเสียหาย) |

| **CMap** | ตารางในไฟล์ PDF ที่แปลงรหัสในฟอนต์กลับเป็นตัวอักษรจริง — CMap เสียทำให้ข้อความอ่านออกมาเพี้ยนทั้งไฟล์ |

| **D-P0 ถึง D-P5** | ขั้นตอนของ DOC-PIPELINE ที่ใช้ทำเอกสารทุกชิ้น: D-P0 เก็บวัตถุดิบ · D-P1 อ่าน source · D-P2 เขียน spec ลงดิสก์ · D-P3 build · D-P4 ผู้ตรวจคุณภาพตรวจ · D-P5 แก้แล้วให้ตรวจซ้ำเฉพาะส่วนที่แก้ (นิยามเต็มอยู่ไฟล์ `~/.claude/agents/iCE-Compass-Next.md` §5) — skill นี้ทำงานที่ขั้น D-P1 |

# §0 หลักการ — ทำไมต้องมี skill นี้

การ "อ่านเอกสาร" ของ fleet เคยเป็นเรื่องต่างคนต่างเดา และมี**ความเสียหายเงียบ** 2 ชนิดที่ไม่มีใครจับได้:

| ความเสียหายเงียบ | เกิดยังไง | ผลที่ตามมา |
|---|---|---|
| **ข้อความไทยพัง** | `pdftotext` ทำสระอำแตก (`จำกัด` → `จ ำกัด`) · LibreOffice ก็เคยทำ | ค้นหาไม่เจอ · copy ไปใช้ต่อผิด · Turnitin/index เพี้ยน |
| **เนื้อหาหายทั้งหน้า** | PDF ที่เป็นภาพสแกน แปลงแล้วได้ข้อความว่าง **แต่ไม่มีใครบอก** | สรุป/อ้างอิงจากข้อมูลที่ขาด โดยคิดว่าครบ (เคสจริง: ไฟล์ 187 หน้า อ่านได้ 138 หน้า) |
| **สระอำยุบเป็นช่องว่าง** (พบ 2026.08.29) | ฟอนต์/CMap ของ PDF ทำให้ "ำ" กลายเป็นช่องว่าง+สระอา (`กำหนด` → `ก าหนด`) — ร้ายกว่าสองแบบบนเพราะ**เคยรอดตัวตรวจ** จนไฟล์เสียถูกเก็บเข้าคลังในสถานะ "ตรวจแล้วสะอาด" (เคสจริง: คู่มือ e-GP RSS เสีย 31 จุด · ไทย 5,705 อักขระแต่สระอำ = 0) | ความเสียหายชนิดเดียวกับแถวแรก แต่ไม่มีใครรู้เลยว่าเสีย — V01R06 ปิดช่องนี้แล้วด้วยกติกาตรวจ 3 ข้อใหม่ใน §3.3 |

⛔ **ทุกขั้นรันในเครื่อง 100%** — ไม่มี API key ไม่มี endpoint ไม่ส่งไฟล์ออกนอกเครื่อง
สัญญา งบการเงิน TOR ลูกค้า เอกสารภายใน ใช้ได้ปลอดภัย (ทั้ง 2 เครื่องมือเป็น Rust binary · MIT license)

# §1 เครื่องมือ — คำสั่งเดียวจบ

```bash
bash ~/.claude/agents/_lib/doc_to_md.sh FILE [-o OUT.md]
bash ~/.claude/agents/_lib/doc_to_md.sh --scan DIR        # กวาด PDF ทั้งโฟลเดอร์ก่อนดูดเข้าคลัง
bash ~/.claude/agents/_lib/doc_to_md.sh FILE --inspect-only   # ดูชนิด PDF อย่างเดียว ไม่แปลง
```

helper ทำ **4 ขั้นให้ตามลำดับ** โดยขั้น ①②③ ทำอัตโนมัติทุกครั้ง ส่วนขั้น ④ ทำเมื่อสั่ง `--ocr` เท่านั้น — agent ไม่ต้องจำลำดับเอง:

```
① คัดกรอง (PDF)   pdf-inspector → หน้าไหนเป็นภาพ อ่านข้อความไม่ได้ → เตือนก่อนแปลง
② แปลง            anydoc        → 16 นามสกุล → GitHub-Flavored Markdown
③ ตรวจไทย         ของเราเอง      → สระอำ/วรรณยุกต์รอดครบไหม  ← ⭐ สองตัวบนไม่มีข้อนี้
④ OCR (เมื่อสั่ง)  macOS Vision  → ⛔ ยังอยู่ในเครื่อง · ~1.8 วินาที/หน้า (วัดได้ 1.75) · ทำ 2 แบบ:
   ④a เติมต่อท้าย  หน้าที่เป็นภาพไม่มีข้อความอยู่แล้ว → OCR เฉพาะหน้านั้นมาเติมส่วนที่ขาด
   ④b แทนที่ทั้งไฟล์ ชั้นข้อความที่มีอยู่**ตรวจไทยไม่ผ่าน** (ฟอนต์/CMap พัง) → OCR ทุกหน้า
      แล้วทิ้งข้อความเดิมทั้งหมด — เพราะการเติมต่อท้ายช่วยไม่ได้ ข้อความเสียยังอยู่ ตรวจก็ยังตก
      (V01R06 — เดิมกรณีนี้ `--ocr` เงียบไม่ทำอะไรเลย เพราะ pdf-inspector มองว่าทุกหน้า "อ่านได้")
```

```bash
bash ~/.claude/agents/_lib/doc_to_md.sh FILE --ocr -o OUT.md      # helper เลือก ④a/④b ให้เองตามผลตรวจ
bash ~/.claude/agents/_lib/doc_to_md.sh FILE --ocr-all -o OUT.md  # บังคับ ④b ทันที ไม่ต้องรอผลตรวจ
```

**exit code (V01R06):**

| code | ความหมาย | agent ต้องทำอะไร |
|---|---|---|
| `0` | สะอาด · หรือเป็นไฟล์ข้อความอยู่แล้วและมีเนื้อหาจริง (`.txt/.md/.json/.html`) → อ่านตรงได้ | ใช้ผลได้ |
| `1` | ไม่พบไฟล์ | ตรวจ path |
| `2` | **อ่านไม่ได้** — ไฟล์ว่าง (รวมไฟล์ข้อความที่ขนาด 0 ไบต์) · ไฟล์เสีย · ฟอร์แมตนอก 16 นามสกุล · แปลงแล้วว่างเปล่า | 🔴 **แจ้ง user + เข้าบันได R2b · ห้ามเดาเนื้อหา** |
| `3` | ข้อความไทยเสียหาย — ตรวจตกข้อใดข้อหนึ่งใน 5 กติกา fail ของ §3.3 (สระอำแตก · วรรณยุกต์ลอย · สระอำยุบเป็นช่องว่าง · สระลอยหลังช่องว่าง · ไทย ≥1,000 อักขระแต่ไม่มีสระอำเลย) | 🔴 หยุด ห้ามเข้าคลัง (R2) · เป็น PDF → ซ่อมได้ด้วยการรันใหม่พร้อม `--ocr` (④b จะแทนที่ชั้นข้อความที่เสีย) |
| `4` | ไม่พบ venv เครื่องมือ | สร้างใหม่ตาม §5 |

# §2 ⭐ กติกาบังคับ — R1 ถึง R5 และ R2b (รวม 6 ข้อ)

> R2b วางไว้ต่อจาก R4 เพราะเป็นบันไดทางออกที่ยาว แต่โดยเนื้อหาเป็นส่วนขยายของ R2 (ใช้เมื่ออ่านไฟล์ไม่ได้หรืออ่านได้ไม่ครบ)

**R1 — ใช้ helper นี้เป็นตัวแปลงมาตรฐาน ห้ามเขียนเองใหม่**
`python-docx` / `pdftotext` / `openpyxl` ยังใช้ได้เมื่อต้องการ **โครงสร้างระดับ XML** (เช่น ตรวจฟอนต์
ตรวจ merge cell) แต่ **การอ่าน "เนื้อหา" เป็นข้อความ/Markdown → ใช้ `doc_to_md.sh` เสมอ**
เหตุผล: มันตรวจภาษาไทยให้ด้วย ซึ่งเครื่องมือเดิมไม่มี

**R2 — 🔴 exit 3 (ข้อความไทยเสียหาย) = หยุด ห้ามเอาเข้าคลัง/ห้ามใช้อ้างอิง**
รายงาน user ว่าเสียหายกี่จุด แล้วขอไฟล์ต้นฉบับใหม่ · **การตัดสินใจรับทั้งที่เสียหายเป็นของ user เท่านั้น**
ถ้า user ยืนยันรับ ให้เก็บได้แต่ต้องบันทึกใน provenance ว่า "ข้อความไทยเสียหาย N จุด — user อนุมัติให้ใช้เมื่อ [วันที่]"
และห้ามใช้ข้อความช่วงที่เสียหายเป็น citation แบบคำต่อคำ · agent ตัดสินใจรับเองไม่ได้
**ห้ามซ่อมข้อความเอง** (เดาว่าคำเดิมคืออะไร = แต่งข้อมูล ผิด H3 anti-hallucination)

**R3 — 🔴 PDF ที่มีหน้าต้อง OCR = ต้องแจ้ง user เสมอ ห้ามเงียบ**
บอกให้ชัดว่า "ไฟล์ 187 หน้า อ่านข้อความได้ 138 หน้า · อีก 49 หน้าเป็นภาพ"
→ user ตัดสินว่าจะหา OCR แยก หรือทำงานจากส่วนที่อ่านได้ · **ห้ามสรุปเนื้อหาโดยไม่บอกว่าขาด**
