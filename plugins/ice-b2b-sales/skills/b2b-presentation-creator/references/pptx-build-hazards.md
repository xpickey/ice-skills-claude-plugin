## 1. อักขระที่ทำให้ PowerPoint ปฏิเสธทั้งไฟล์ (ตรวจเป็นด่านแรกเสมอ)

ตรวจข้อความในไฟล์ก่อนแปลงเป็นภาพใด ๆ เพราะด่านนี้ถูกที่สุดและจับความเสียหายที่ร้ายแรงที่สุด อ่านข้อความออกมาด้วย python-pptx ไม่ต้องใช้เครื่องมือแปลงภาพ

| อักขระ | รหัส | ให้ใช้แทนด้วย | เหตุผล |
|---|---|---|---|
| `→` | U+2192 | `▸` (U+25B8) | PowerPoint บน Mac ปฏิเสธทั้งไฟล์และบังคับให้กด Repair · `▸` สื่อทิศทางเหมือนกันและเปิดได้ทุกเครื่องยนต์ |
| `⟶` `➜` `➔` `➙` | U+27F6 · U+2799 · U+2794 · U+2799 | `▸` (U+25B8) | วงศ์เดียวกัน ความเสี่ยงเดียวกัน |

- สายการสร้างไฟล์ `_lib/build_pptx.py` แทนที่อักขระเหล่านี้ให้อัตโนมัติตอนสร้าง และ `scripts/deck_qa.py` ตรวจซ้ำเป็นตาข่ายรอง
- ถ้าเขียนหรือวางข้อความสไลด์ด้วยมือ ให้เปลี่ยน `→` เป็น `▸` เอง อย่าใช้สายตาตัดสิน เพราะข้อบกพร่องนี้มองไม่เห็นในภาพตัวอย่างของ LibreOffice
- **LibreOffice และ qlmanage เป็นภาพตัวอย่างเท่านั้น ไม่ใช่การตรวจรับ** ทั้งสองเปิดไฟล์ที่มีอักขระเหล่านี้ได้ตามปกติ จึงเป็นการผ่านลวง เครื่องมือทั้งสองยังมองไม่เห็นอัตราส่วนที่เพี้ยนจาก 16:9 ไฟล์ที่เสียหาย และคำเตือนเรื่องฟอนต์ที่ PowerPoint จริงแสดง
- **วิธีหาต้นเหตุเมื่อไฟล์ถูกขอให้ซ่อม** ให้แบ่งไฟล์ครึ่งหนึ่งทีละรอบแล้วเปิดดูว่าครึ่งใดพัง จนเหลือหน้าเดียว อย่าไล่อ่าน content-spec เพื่อหาอักขระ เพราะอักขระที่เป็นต้นเหตุมักอยู่ในรูปทรงเดียว
- *กรณีจริง:* งาน KT Food S4 มีอักขระ `→` ตัวเดียวทำให้ทั้งไฟล์เปิดไม่ได้ ทั้งที่ LibreOffice รายงานว่าผ่าน

## 2. การตัดบรรทัดภาษาไทย — PPTX กับ HTML ใช้กลไกคนละตัว

ภาษาไทยไม่มีช่องว่างระหว่างคำ เครื่องยนต์ทั้งสองจึงตัดคำกลางพยางค์ เช่น "ภาคผนว" ขึ้นบรรทัดใหม่ว่า "ก" ถ้าไม่สั่งให้ทำอย่างอื่น วิธีแก้ของสองรูปแบบไม่เหมือนกัน อย่านำวิธีของฝั่งหนึ่งไปใช้กับอีกฝั่ง

| รูปแบบผลลัพธ์ | กลไกที่ทำงานจริง | สิ่งที่ต้องใส่ | สิ่งที่ต้องไม่ทำ |
|---|---|---|---|
| **PPTX** | พจนานุกรมไทยของ PowerPoint เอง | `lang="th-TH"` บนทุก run ที่มีอักษรไทย (`a:rPr lang`) ใน python-pptx คือ `run.font.language_id` | อย่าใส่อักขระช่องว่างที่มองไม่เห็นเป็นค่าเริ่มต้น |
| **HTML** | พจนานุกรมไทยของเบราว์เซอร์ สั่งผ่าน CSS | `lang="th"` บนอิลิเมนต์ พร้อม `word-break: normal` และ `line-break: loose` | `word-break: break-all` ตัดทุกคำที่ขอบกล่อง ซึ่งคือข้อบกพร่องที่กำลังจะแก้พอดี |

**ป้องกันตั้งแต่ตอนออกแบบได้ผลกว่าทั้งสองวิธี** กำหนดความกว้างกล่องข้อความไว้ประมาณ 1.15 ถึง 1.20 เท่าของเนื้อหาเดียวกันที่เป็นอักษรละติน และวางคำไทยยาวที่ห้ามถูกตัดให้อยู่บรรทัดเดียว เช่น การประปาส่วนภูมิภาค · ภาคผนวก · คณะกรรมการ · ระบบสารสนเทศ

**ตรวจก่อนสร้างไฟล์** `python3 ~/.claude/agents/_lib/thai_wordbreak.py --check "<ข้อความ>" --width <จำนวนตัวอักษร>` ซึ่งใช้ PyThaiNLP เครื่องยนต์ `newmm` · อย่าใช้เครื่องยนต์ `longest` เพราะเปลี่ยนอักษรอังกฤษเป็นตัวพิมพ์เล็ก · ถ้าคำสั่งรายงานว่าขาดไลบรารี ให้ทำตามคำสั่งติดตั้งที่เครื่องมือพิมพ์ออกมาแล้วรันซ้ำ

**อักขระช่องว่างที่มองไม่เห็น (ZWSP · U+200B) เป็นทางเลือกสุดท้ายเท่านั้น** อักขระนี้บังคับจุดตัดบรรทัดได้จริง แต่ทำให้การค้นหาคำนั้นด้วย Ctrl+F ไม่เจอ และติดไปกับข้อความเวลาคัดลอก จึงใช้กับงาน TOR งาน e-GP และเอกสารที่ผู้อ่านต้องค้นหาคำไม่ได้ กติกาฉบับเต็มอยู่ที่สกิล `ice-doc-builder` หัวข้อ 3.5 · ผู้ตรวจคุณภาพจับเรื่องนี้เป็น D7.7 และ D7.H8

## 3. ฟอนต์ — ใครรับผิดชอบส่วนใด

เอกสารสองภาษาจะแสดงผลถูกต้องบนเครื่องผู้รับก็ต่อเมื่อฟอนต์ไทยและอังกฤษถูกฝังมากับไฟล์ เรื่องนี้มีสามส่วนและแต่ละส่วนมีเจ้าของคนละราย สกิลสร้างสไลด์จึงไม่เขียนกติกาซ้ำ

| ส่วน | เจ้าของเรื่อง | สิ่งที่สกิลสร้างสไลด์ต้องทำ |
|---|---|---|
| **เลือกฟอนต์ที่ฝังได้** (ฟอนต์แบบ static · ค่า fsType ไม่ใช่ Restricted · คู่ฟอนต์สัญญาอนุญาต SIL OFL ตรวจค่า fsType รายฟอนต์ด้วย fontTools) | สกิล `b2b-slide-designer` หัวข้อ 5.5.1 ซึ่งเป็นเจ้าของเรื่องตัวอักษรทั้งหมด | เลือกจากรายชื่อที่สกิลนั้นอนุญาต แล้วส่งต่อลงมาใน content-spec |
| **ลงมือฝังฟอนต์** (5 เงื่อนไขที่ PowerPoint ยอมรับ ได้แก่ วาง `embeddedFontLst` ต่อจาก `notesSz` · แปลงไฟล์ฟอนต์ทุกตัวผ่าน fontTools ให้เป็นรูปแบบมาตรฐาน · ตั้งชนิดเนื้อหาเป็น `application/x-fontdata` · ตั้ง `embedTrueTypeFonts="1"` และ `saveSubsetFonts="0"`) | เครื่องมือสร้างไฟล์ `_lib/embed_fonts_pptx.py` | ส่งงานให้เครื่องมือนั้นทำ ไม่ฝังฟอนต์เอง |
| **ตรวจว่าฝังสำเร็จ** | `_lib/validate_pptx_fonts.py` แล้วเปิดไฟล์ใน PowerPoint จริง | ต้องได้ผล PASS ก่อนส่งมอบทุกครั้งสำหรับงานที่ถึงมือลูกค้า |

⛔ **อย่าใช้ LibreOffice `--convert-to pptx:…EmbedFonts` ฝังฟอนต์** เพราะพิสูจน์แล้วว่าไม่ได้ฝังจริง (เขียนฟอนต์ลงเฉพาะไฟล์ `.odp`) และยังเขียนทับค่าขนาดสไลด์ `sldSz` เป็นอัตราส่วน 4:3 ซึ่งทำลายงาน 16:9 ทั้งชุด การตรวจรับขั้นสุดท้ายต้องเปิดใน PowerPoint จริงเท่านั้น เพราะ qlmanage และ LibreOffice เป็นการผ่านลวง มองไม่เห็นคำเตือน General Failure ของฟอนต์

**เมื่อเครื่องไม่มีฟอนต์ที่เลือก** ให้ติดตั้งด้วย `scripts/install_fonts.sh` (ใช้ได้บน Linux และ Mac) หรือถ้าติดตั้งไม่ได้ ให้ใช้ฟอนต์ระบบที่ใกล้เคียงที่สุดแล้วบันทึกการเปลี่ยนตัวนั้นไว้ในรายงานตรวจ เพื่อให้ผู้ตรวจและ user รู้ว่าไฟล์นี้ไม่ได้ใช้ฟอนต์ตามที่ออกแบบไว้

**ฟอนต์ตามเนื้อหา ไม่ใช่ตามแม่แบบ** ค่า `font_strategy` ที่ `b2b-slide-designer` ส่งมามีสามโหมด คือ ไทยล้วน · อังกฤษล้วน · ไทยและอังกฤษอยู่ในกล่องเดียวกัน แต่ละโหมดมีสองวิธีเลือกฟอนต์

- `unified` ใช้ฟอนต์ตัวเดียวที่มีทั้งอักษรไทยและละติน (เช่น IBM Plex Sans Thai หรือ Sarabun) ใส่ทั้งช่องละตินและช่องอักษรไทย
- `pair` ใช้ฟอนต์ละตินกับฟอนต์ไทยคนละตัว ผ่านการกำหนดชื่อฟอนต์ครบสามช่องในทุก text run (ช่องอังกฤษ · ช่องเอเชียตะวันออก · ช่องภาษาไทย) ซึ่งคือวินัย D1 ของสกิล `ice-doc-builder` และปรับความสมดุลตามหัวข้อ 5.5 ของ `b2b-slide-designer`
- **ขนาดตัวอักษร** อักษรไทยตั้งใหญ่กว่าละติน 1 ถึง 2 พอยต์ (วินัย D3) · โหมดเอกสารอ่านเอง ลดขนาดตัวเนื้อลงหนึ่งขั้น · โหมดนำเสนอสด เพิ่มขนาดหัวเรื่องขึ้น
- **สลับฟอนต์อัตโนมัติกันอักษรไทยแตก** ถ้าแม่แบบหรือ content-spec ระบุฟอนต์ที่มีเฉพาะอักษรละติน แต่เนื้อหามีอักษรไทย ให้เปลี่ยนไปใช้ `unified` หรือ `pair` โดยไม่รอให้สั่ง

## 4. ชุดตรวจรับของสไลด์ที่ส่งออกเป็น HTML

ใช้เมื่อผลลัพธ์เป็น HTML หรือทั้งสองรูปแบบ รายละเอียดการสร้างอยู่ที่ `13-html-deck-builder.md` หัวข้อ 5

- **ล็อกอัตราส่วน 16:9** เปิดในเบราว์เซอร์จริงแล้วย่อขยายหน้าต่าง เวทีทั้งหมดต้องย่อขยายตามไปพร้อมกัน เนื้อหาต้องไม่ไหลจัดเรียงใหม่
- **ไม่มีเนื้อหาล้นหรือทับกัน** ทุกสไลด์ต้องอยู่ในเวทีขนาด 1920 คูณ 1080 และไม่มีแผงใดชนกัน
- **ค่าคอนทราสต์ตามมาตรฐาน WCAG อย่างน้อย 4.5:1** และตั้งเป้าที่ 7:1 สำหรับงานที่ฉายขึ้นจอ ตรวจทั้งตัวอักษรเทียบพื้นหลังและสีเน้นเทียบพื้นหลัง ถ้าตัวอักษรวางบนภาพให้ตรวจเก้าจุดกระจายทั่วภาพ
- **ทดสอบขนาดหน้าจออื่น** ที่ 1280 คูณ 720 และหน้าจอโทรศัพท์หนึ่งขนาด ต้องขึ้นแถบดำบนล่างอย่างถูกต้อง ไม่ใช่เพี้ยน
- **ใช้งานด้วยแป้นพิมพ์และการสัมผัสได้** และเคารพการตั้งค่า `prefers-reduced-motion` ของผู้ใช้
- **ไม่มีอักขระ `→` หลงเหลือ** สคริปต์ `build_html.py` เปลี่ยนให้เป็น `▸` อยู่แล้วเพื่อให้ปลอดภัยข้ามรูปแบบไฟล์ แต่ให้ตรวจซ้ำ
- **การตรวจรับต้องมาจากเบราว์เซอร์จริง** (Chrome หรือ Safari) หรือภาพหน้าจอจาก Playwright · LibreOffice ไม่เกี่ยวข้องกับงาน HTML เลย · การตรวจอิสระเป็นหน้าที่ของอริสในสาย HTML ของมิติ D7 ซึ่งทำในบริบทแยกจากผู้สร้าง
