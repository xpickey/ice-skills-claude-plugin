# B2B Slide Designer และคลังอ้างอิงการออกแบบ

> **Version:** V03R01 | **Date:** 2026.09.05 | ประวัติรุ่นทั้งหมดอยู่ที่ `references/skill-changelog.md`
> **ไฟล์นี้ใช้ทำอะไร:** เป็นคู่มือของผู้ที่ต้อง**ออกแบบ**งานนำเสนอ คือตัดสินว่าใช้แม่แบบใด ชุดสีใด ฟอนต์ใด ไอคอนชุดใด และวางเลย์เอาต์อย่างไร แล้วเขียนผลออกมาเป็น design spec · สกิลนี้ไม่สร้างไฟล์เอง ผู้สร้างไฟล์คือ `b2b-presentation-creator` และเครื่องมือ build ของ `ice-doc-builder`
> **ของที่มีให้ใช้:** แม่แบบหลัก 8 ชุด และคลังอ้างอิง 1,186 รายการ (ตัวอย่างงานตามอุตสาหกรรม · เอกสารนำเสนอแนวที่ปรึกษา · ไฟล์แม่แบบกรอบการวิเคราะห์ · ชุดสีไล่เฉด · แบบอินโฟกราฟิก · ไอคอน) พร้อมตัวช่วยเลือกในหัวข้อ 4.5 · design spec ที่ออกมาใช้ได้กับทุกรูปแบบผลลัพธ์

## 0. กฎประจำที่ใช้กับสไลด์ทุกชุด — อ่านก่อนเริ่มงานเสมอ

**บ้านเดียวของกฎออกแบบประจำคือ `references/pptx-design-doctrine.md`** เปิดอ่านไฟล์นั้นก่อนตัดสินใจออกแบบทุกครั้ง ที่ปลายทางมีกฎ 6 ข้อพร้อมเหตุผลและวิธีตรวจ ได้แก่ ภาษาบนสไลด์เป็นภาษาธุรกิจไม่บรรยาย · หน้าเนื้อหาทุกหน้ามีภาพหรือแผนภาพและไอคอน · สีไล่เฉดโดยเลือกจากคลังที่มีอยู่ ไม่คิดสีขึ้นเอง · สีที่บอกความหมายต้องคงเส้นคงวาทั้งเล่ม · หนึ่งหน้าหนึ่งข้อความและหัวเรื่องเป็นประโยคสรุป · เขียนจากมุมประโยชน์ของลูกค้าและต่อยอดจากไฟล์รุ่นล่าสุดเสมอ

กฎทั้ง 6 ข้อนั้นใช้กับสไลด์ทุกชุดที่ลูกค้าหรือผู้บริหารจะเห็น ไม่ว่าจะใช้แม่แบบของ iCE แม่แบบของลูกค้า หรือแม่แบบทั่วไป และใช้โดยที่ user ไม่ต้องสั่งหรือเอ่ยชื่อสิ่งใดก่อน · ส่วน "iCE Super Template" (แม่แบบปกเข้มลายทอง) เป็นคนละเรื่องกัน แม่แบบนั้นยังใช้เฉพาะเมื่อ user เอ่ยชื่อเท่านั้น และสูตรการผลิตอยู่ที่ `ice-doc-builder/references/ice-super-template.md`

## 0.1 ตารางนิยาม — คำและรหัสที่ไฟล์นี้ใช้

| คำหรือรหัส | ความหมาย |
|---|---|
| **doctrine** | ไฟล์กฎออกแบบประจำตามหัวข้อ 0 คือ `references/pptx-design-doctrine.md` |
| **design spec** | เอกสารกำหนดรูปแบบงานนำเสนอที่เขียนก่อนลงมือสร้าง ระบุโครงหน้า ลำดับขนาดตัวอักษร ชุดสี ชุดไอคอน และรูปแบบผลลัพธ์ |
| **content-spec** | ไฟล์ที่ระบุเนื้อหารายหน้าของงานนำเสนอ เป็นที่อยู่ของช่อง `mode` `objective` `action_title` `topic_id` `color_set` `palette_base` ตามที่ doctrine กำหนด |
| **DESIGN BRIEF** | ชุดคำถามตั้งโจทย์ก่อนวาดงานนำเสนอหรืออินโฟกราฟิก รายละเอียดอยู่ที่หัวข้อ 4.11 |
| **`ICE_DESIGN=briefed`** | คำประกาศที่เติมไว้หน้าคำสั่งสร้างไฟล์ แปลว่าทำ DESIGN BRIEF ครบแล้ว บ้านเดียวของเครื่องหมายนี้คือหัวข้อ 4.11.1 |
| **`ICE_BUILD=pipeline`** | คำประกาศที่เติมไว้หน้าคำสั่งสร้างไฟล์ แปลว่างานนี้เดินตามสายงานสร้างเอกสารของทีม เอกสารอยู่ที่สกิล `ice-doc-builder` |
| **ตัวตรวจก่อนสร้างไฟล์** | สคริปต์ `~/.claude/hooks/ice-prebuild-guard.sh` ที่ระบบเรียกอัตโนมัติก่อนคำสั่งสร้างเอกสารทำงาน หน้าที่คือปฏิเสธคำสั่งที่ยังไม่ผ่านเงื่อนไข |
| **โหมด presenter และ document** | โหมดของงานนำเสนอ ประกาศหนึ่งค่าต่อชุดในช่อง `mode` ของ content-spec · presenter คือใช้พูดสด งบคำต่อหน้าไม่เกิน 25 คำ · document คือให้อ่านเอง ไม่เกิน 75 คำ · ไม่ระบุถือเป็น document |
| **Corporate Identity** | คู่มืออัตลักษณ์องค์กร ระบุสี ฟอนต์ และการใช้โลโก้ ของ iCE เองหรือของลูกค้า |
| **อริส** | ชื่อเล่นของ agent `qa-master-agent` ผู้ตรวจคุณภาพงานก่อนถึงลูกค้า ตรวจงานออกแบบในมิติ D6 เรื่องแบรนด์และรูปแบบ และ D7 เรื่องเลย์เอาต์ |

## 1. สิ่งที่สกิลนี้ทำได้

1. **ผูกกับอัตลักษณ์องค์กร** — ทุกแม่แบบผสานสีหลักของ iCE (`#1E66A4`) และสีรอง (`#41A8B5`) ให้อัตโนมัติ
2. **เลือกแม่แบบให้ตรงงาน** — ตามวัตถุประสงค์ ผู้ฟัง และโทนของงาน ด้วยตารางในหัวข้อ 3
3. **ออกคู่มือการออกแบบที่ละเอียดพอลงมือทำ** — รหัสสี ชุดฟอนต์ ระบบกริด ระยะห่าง ไอคอน และรูปแบบเลย์เอาต์
4. **ใช้ได้ทุกรูปแบบผลลัพธ์** — spec เดียวใช้กับ PPTX HTML PDF และ Word (หัวข้อ 4.5 ขั้นที่ 6)
5. **มีเลย์เอาต์ 15 แบบต่อแม่แบบหนึ่งชุด** — เลือกตามประเภทเนื้อหาของแต่ละหน้า
6. **มีตัวช่วยเลือกจากคลัง 1,186 รายการ** — หัวข้อ 4.5 เลือกเองเมื่อชัด และเสนอตัวเลือก 5 รายการเมื่อกำกวม
7. **เลือกฟอนต์ตามภาษา** — หัวข้อ 4.6 และรายการฟอนต์ที่อนุมัติในหัวข้อ 5.5
8. **ใช้ไอคอนจากคลังก่อนสร้างใหม่** — หัวข้อ 4.7

## 4. ขั้นตอนการใช้งาน

1. **ตั้งโจทย์จากผู้ฟัง** — ผู้ฟังคือใคร · ต้องการโทนแบบใด (เป็นทางการ สร้างสรรค์ เทคนิค หรือใช้ภายใน) · ใช้ที่ไหน (ฉายในห้องประชุม พิมพ์ อ่านบนจอ หรือแนบไปกับอีเมล)
2. **เลือกแม่แบบ** — ใช้ตารางหัวข้อ 3 เป็นเครื่องมือคัดกรอง ไม่แน่ใจให้ใช้ iCE-CI เป็นค่าเริ่มต้น
3. **เปิดไฟล์อ้างอิงของแม่แบบที่เลือก** — `references/template_<ชื่อ>.md` โดยชื่อคือ `linen` `arctic` `cobalt` `onyx` `amber` `whiteboard` `ice_ci` `ice_propose` · แฟ้ม `template_ice_propose.md` ใช้กับงานข้อเสนอ สถาปัตยกรรม และแผนงานที่ต้องการอินโฟกราฟิกแบบสามมิติ
4. **เลือกเลย์เอาต์** — ไฟล์อ้างอิงแต่ละชุดมีเลย์เอาต์ 15 แบบ ตั้งแต่หน้าปก หน้าคั่นบท สองคอลัมน์ หน้านำด้วยภาพ หน้านำด้วยข้อมูล หน้าคำพูด หน้ากระบวนการ หน้าเปรียบเทียบ ไปจนถึงหน้าปิด
5. **ส่งต่อให้ผู้สร้างไฟล์** — งาน PPTX ส่งให้สกิล `pptx` หรือ `b2b-presentation-creator` · งาน Word ส่งให้สกิล `docx` · งาน HTML และ PDF ส่งให้ `b2b-presentation-creator` ตามหัวข้อ 5.6

## 4.4 การตรวจก่อนเริ่มสร้างงานนำเสนอ

**ด่านนี้อยู่ตรงไหนของลำดับงาน** เดินหลังจากเลือกแม่แบบและเปิดไฟล์อ้างอิงของแม่แบบแล้วตามหัวข้อ 4 ขั้นที่ 1 ถึง 3 และเดินให้จบก่อนส่งงานให้ผู้สร้างไฟล์ตามหัวข้อ 4 ขั้นที่ 5 · การนับขั้นที่ 1 ถึง 5 ในหัวข้อนี้เป็นการนับภายในของด่านนี้เอง คนละชุดกับขั้นที่ 1 ถึง 5 ของหัวข้อ 4

หัวข้อนี้คือเนื้อหาทั้งหมดของสกิล `pre-flight-deck` ที่ยุบเข้ามาไว้ที่นี่ **เมื่อไฟล์ฉบับนี้ถูกนำไปใช้งานจริง สกิล `pre-flight-deck` จะถูกลบออกจากคลังสกิล** เพราะการตรวจก่อนสร้างกับการออกแบบเป็นงานของคนเดียวกันและอยู่คนละไฟล์ทำให้ไม่มีใครเปิดอ่าน · เหตุผลที่ต้องมีด่านนี้คือ deck ที่เนื้อหาถูกแต่หน้าตาจืด ซึ่งมาจากห้าอาการเดิม ๆ คือไม่เปิดไฟล์อ้างอิงในโฟลเดอร์ `references/` เลย · ใช้วิธีวาดด้วยรูปทรงพื้นฐานทุกหน้าโดยไม่พิจารณาวิธีอื่น · ใช้เลย์เอาต์เดิมซ้ำทั้งเล่ม · ใส่ข้อมูลตัวอย่างที่ไม่สมจริง · ข้ามคลังไอคอน ความหมายของสี และตัวเลขเด่นประจำหน้า

**กรณีที่ต้องเดินด่านนี้** สร้าง deck ใหม่ทุกขนาด · รื้อออกแบบ deck เดิมครั้งใหญ่ · เพิ่มสไลด์ตั้งแต่ 3 หน้าขึ้นไปในชุดเดิม · แปลงเอกสาร Markdown หรือ Word เป็นสไลด์ · ทำ deck ให้ผู้ฟังระดับผู้บริหารสูงสุด · ทำใหม่หลังจากงานครั้งก่อนออกมาไม่ดี · งานที่ดูง่ายก็ยังต้องเดิน เพราะต้นทุนของการตรวจต่ำกว่าต้นทุนของการรื้อทำใหม่มาก

**ขั้นที่ 1 ทำรายการไฟล์อ้างอิงที่จะอ่าน** ไฟล์ของผู้สร้างอยู่ที่โฟลเดอร์ `b2b-presentation-creator/references/` (ปัจจุบันมี 13 ไฟล์ ไฟล์ที่สำคัญที่สุดคือ `06-layouts.md` `07-infographics.md` `08-color-system.md` และ `12-quality-charter.md`) แล้วประกาศออกมาว่าจะอ่านกี่ไฟล์

**ขั้นที่ 2 อ่านทุกไฟล์แล้วสรุปสิ่งที่ได้** เขียนสรุปหนึ่งบรรทัดต่อไฟล์ จากนั้นประกาศความเข้าใจสี่เรื่อง คือจะใช้เลย์เอาต์แบบใดบ้าง · จะผสมวิธีทำภาพแบบใดบ้าง · ความหมายของสีในเล่มนี้คืออะไร · จะใช้ฟอนต์คู่ใดสำหรับหัวเรื่องและเนื้อความ · เปิดไฟล์ใดไม่ได้ให้หยุดแล้วถาม user

**ขั้นที่ 4 ตัดสินตามความมั่นใจ** คะแนนนำห่างชัดเจนหลังหักและเพิ่มคะแนนแล้ว ให้เลือกเองทันทีพร้อมบอกว่าเลือกอะไรเพราะอะไร · คะแนนใกล้กันหลายตัว ให้เสนอ 5 อันดับแรกพร้อมเหตุผลรายตัวให้ user เลือก · ตัวที่ได้คะแนนนำเป็นกรอบการวิเคราะห์เฉพาะทางที่โจทย์ไม่ได้ขอ ให้เสนอ 5 ตัวเลือกเสมอแทนการเลือกเอง · user ไม่ระบุรายละเอียดก็เดินต่อได้ด้วยค่าเริ่มต้น คือโทนตามอุตสาหกรรมและแม่แบบ iCE-Propose

**การตัดคำภาษาไทย ต้องเผื่อความกว้างตั้งแต่ตอนออกแบบ** ภาษาไทยไม่มีช่องว่างระหว่างคำ กล่องข้อความหรือคอลัมน์ที่แคบเกินไปจะถูกโปรแกรมผ่ากลางคำ เช่น "ภาคผนว" ขึ้นบรรทัดใหม่เป็น "ก" · ตอนกำหนดขนาดกล่องข้อความและความกว้างคอลัมน์ ให้เผื่อความกว้าง 1.15 ถึง 1.20 เท่าของข้อความละตินที่มีความหมายเดียวกัน และให้คำไทยยาวที่พบบ่อยในงานของทีมจบในบรรทัดเดียว ได้แก่ "การประปาส่วนภูมิภาค" (19 ตัวอักษร) "ภาคผนวก" "ผู้รับจ้าง" "คณะกรรมการ" "ระบบสารสนเทศ" กล่องที่แคบกว่านั้นถือว่าออกแบบผิด · ตรวจก่อนส่ง design spec ด้วยคำสั่ง `python3 ~/.claude/agents/_lib/thai_wordbreak.py --check "ข้อความ" --width N` ซึ่งบอกว่าข้อความนั้นถูกตัดกลางคำที่ความกว้างเท่านี้หรือไม่ ถ้าผลออกมาว่าถูกตัด ให้เพิ่มความกว้างของกล่องแล้วตรวจซ้ำ · การตัดบรรทัดกลางคำเป็นข้อบกพร่องระดับเลย์เอาต์ที่อริสจับในมิติ D7.7 แก้ที่ความกว้างของกล่อง ไม่แก้ที่ตัวอักษร · การแทรกอักขระช่องว่างที่มองไม่เห็น (ZWSP) ไม่ใช่ทางแก้ของขั้นออกแบบ เพราะทำให้การค้นหาข้อความในไฟล์ใช้ไม่ได้ เป็นทางเลือกสุดท้ายของขั้นสร้างไฟล์เท่านั้น

เมื่อได้ข้อสรุปแล้ว ให้ใส่กลยุทธ์ฟอนต์ลงใน design spec ส่งให้ `b2b-presentation-creator` นำไปสร้างไฟล์ต่อ

## 4.7 ใช้ไอคอนจากคลังก่อนสร้างใหม่

ลำดับการใช้ไอคอนมีสามขั้น (1) ค้นในคลัง 401 ชิ้นตาม `references/catalog-icons.md` ซึ่งเป็นไฟล์เวกเตอร์ที่กำหนดสีจากภายนอกได้ หาตัวที่ตรงความหมายที่ต้องการ (2) เปลี่ยนสีให้ตรงชุดสีของงานแล้ววางลงในหน้า (3) ใช้เครื่องมือ AI สร้างไอคอนใหม่เฉพาะเมื่อคลังไม่มีตัวที่ต้องการจริง หรือเมื่อต้องการสไตล์ที่ต่างออกไปจริง เช่น ภาพสามมิติ ภาพเสมือนจริง หรือไอคอนเฉพาะของแบรนด์ · ลำดับนี้ประหยัดเครดิต ทำให้ไอคอนทั้งเล่มเป็นชุดเดียวกัน และเร็วกว่าการสร้างใหม่

## 4.8 ด่านกันร่องรอยงานที่ดูออกว่าทำด้วย AI

เครื่องมือ AI มีหน้าตาค่าเริ่มต้นที่ทุกคนได้เหมือนกัน ทำให้งานดูเหมือนกันไปหมด ด่านนี้ตรวจก่อนปล่อย design spec · เป็นคนละชั้นกับด่านภาษาของอริสในมิติ D5 ซึ่งตรวจสำนวน และคนละชั้นกับกฎออกแบบเชิงบวก 20 ข้อใน `references/design-principles.md` ซึ่งบอกว่าทำอย่างไรให้ถูก ส่วนด่านนี้บอกว่าอะไรคือร่องรอยที่ต้องเลี่ยง

**ห้าข้อที่พบบ่อยที่สุด ตรวจทุกเล่ม** (1) หัวเรื่องตัวเอียง ซึ่งเป็นร่องรอยอันดับหนึ่ง ให้ใช้ตัวตรงเสมอแล้วเน้นด้วยน้ำหนัก สี หรือเส้นใต้ (2) การไล่เฉดจากม่วงไปน้ำเงิน โดยเฉพาะบนตัวอักษร ให้เลี่ยง ส่วนแสงนวลเป็นวงบนพื้นหลังใช้ได้ไม่เกิน 20% ของพื้นที่ (3) การจัดทุกองค์ประกอบไว้แกนกลาง ให้สลับแนวการจัดวาง และมีของอยู่กลางไม่เกินสองชิ้น (4) การใช้ emoji แทนไอคอนประจำหัวข้อ ให้ใช้ไอคอนจากคลัง 401 ชิ้นชุดเดียวทั้งเล่ม (5) ตัวเลขที่กุขึ้นเอง ให้ใส่ขีดคั่นไว้แทนพร้อมข้อความว่ารอยืนยันตัวเลข ตัวเลขทุกตัวมาจาก user เท่านั้น

ด่านเสริมอีก 13 ข้ออยู่ที่ `references/anti-slop-gates.md` ครอบคลุมฟอนต์ที่ไม่ใช้ · การใช้ฟอนต์เกินสามตระกูล · น้ำหนักฟอนต์บางกว่า 300 · สีเน้นเกิน 5% ของพื้นที่ · การใช้ดำสนิทหรือขาวสนิท · สีเทาที่ไม่ผสมสีเน้น · การ์ดไอคอนเรียงเป็นตาราง · การ์ดซ้อนในการ์ด · แถบสีข้างหน้า · ระยะห่างที่ไม่เป็นระบบ · ของตกแต่งที่ไม่สื่อความหมาย · ภาพจำลองหน้าจอปลอม · และข้อผิดพลาดตัวอักษรสีเข้มบนพื้นเข้ม · งานที่ส่งถึงลูกค้าตรวจทุกข้อ งานภายในและงานร่างเน้นห้าข้อแรก

## 4.9 การสร้างชุดสีใหม่เมื่อคลังสีไม่เข้ากับงาน

ปกติให้เลือกชุดสีจากคลัง แต่ถ้าเข้าเงื่อนไขข้อใดข้อหนึ่งต่อไปนี้ ให้พิจารณาสร้างชุดสีขึ้นใหม่เอง คือ user ขอชุดสีเฉพาะหรือขอให้เป็นสีแบรนด์ของตน · user ให้รหัสสีหรือชื่อสีของแบรนด์มา · user บอกอารมณ์งานตั้งแต่สามคำขึ้นไปที่คลังไม่มี · user แนบภาพตัวอย่างอารมณ์งานหรือแถบสีมา · เมื่อเข้าเงื่อนไข ให้ถามหนึ่งครั้งว่าจะสร้างชุดสีใหม่หรือใช้จากคลังซึ่งเร็วกว่า **ขั้นตอนสร้างชุดสีทั้งหมดอยู่ที่ `references/custom-theme-generation.md`** ที่ปลายทางมีลำดับการสร้างหกขั้นตั้งแต่สีเน้นจนถึงการจับคู่ฟอนต์ พร้อมวิธีหมุนแนวทางกันชุดสีซ้ำกันสองรอบติด · ชุดสีของ iCE ยังเป็นฐานตั้งต้นเสมอ

## 4.10 โหมดตรวจงานเดิมและโหมดถอดแนวทางจากงานที่ชอบ

**โหมดตรวจงานเดิม** รับ deck หรือภาพที่มีอยู่แล้วมาให้คะแนน โดยวินิจฉัยอย่างเดียวไม่แก้ไขให้ · วิธีตรวจคือไล่ตามด่านหัวข้อ 4.8 กฎออกแบบ 20 ข้อใน `design-principles.md` และการให้คะแนน 6 แกนของ `b2b-presentation-creator` หัวข้อ 0.5 · ผลลัพธ์เป็นรายการสิ่งที่ควรแก้เรียงตามความสำคัญพร้อมเหตุผลรายข้อ ส่งให้ user ตัดสินว่าจะแก้ข้อใด

**โหมดถอดแนวทาง** รับงานที่ user ชอบมาถอดว่าแนวทางการออกแบบคืออะไร โดยไม่ลอกภาพ · ดูห้าเรื่องคือพื้นและสีเน้นพร้อมสัดส่วนพื้นที่ · บทบาทของตัวอักษรหัวเรื่องกับเนื้อความ (ถ้าเป็นภาพจะระบุชื่อฟอนต์ตรงตัวไม่ได้) · โครงเรื่องและแบบแผนของการเรียงหน้า · จังหวะการเผยเนื้อหา · และความหนาแน่นกับความสมมาตรของหน้า · ผลลัพธ์เป็นบทวินิจฉัยหนึ่งหน้า แล้วถาม user ว่าจะสร้างงานตามแนวทางนี้ เปลี่ยนหนึ่งแกน หรือดูไว้เฉย ๆ · งานที่ปฏิเสธคือแม่แบบที่มีลิขสิทธิ์ขาย ส่วนงานที่มีลายเซ็นเฉพาะตัวของผู้ออกแบบ ให้ถอดแนวทางได้แต่ไม่ลอกท่าเฉพาะตัวนั้นมาทั้งดุ้น · ภาพของ user เองหรือภาพสาธารณะใช้ได้

การรื้อออกแบบใหม่ (redesign) เป็นงานของ `b2b-presentation-creator` หัวข้อ 0.5 จึงไม่เขียนซ้ำที่นี่

## 4.11 การตั้งโจทย์ก่อนวาดอินโฟกราฟิกและไอคอน

หัวข้อนี้เป็นบ้านเดียวของเรื่องนี้ทั้งทีม ที่มาคือคู่มือการทำอินโฟกราฟิกที่ user มอบให้เมื่อ 2026.08.17 ผสานกับหลักสากลสายการนำเสนอข้อมูลและมาตรฐานระบบไอคอน · ผู้ใช้คือทุก agent ที่สร้างงานนำเสนอ · เปิดอ่านหัวข้อนี้ทุกครั้งที่งานต้องสร้างอินโฟกราฟิกหรือไอคอน แล้วเป็นผู้นำการตั้งโจทย์เองก่อนลงมือวาดเสมอ

**หลักใหญ่คือ ตัด แล้ว จัด แล้วจึง วาด** สองขั้นแรกเป็นงานคิด

| ขั้น | ทำอะไร และใครทำ |
|---|---|
| **ตัด** | เลือกว่าอะไรต้องอยู่ในภาพและอะไรตัดทิ้ง user เป็นผู้ตัดสิน agent ช่วยคัดและต้องบอกทุกครั้งว่าตัดอะไรออกด้วยเหตุผลใด |
| **จัด** | เลือกโครงภาพจากคำถามที่อยู่ในหัวคนอ่าน agent เสนอสองทางพร้อมข้อดีข้อเสียของแต่ละทางให้ user เลือกก่อน แล้วจึงวาด |
| **วาด** | สร้างตามสเปกที่ชัดแล้ว agent ทำเอง จากนั้นตรวจย้อนกลับ |

ความผิดพลาดอันดับหนึ่งคือกระโดดจากเอกสารไปขั้นวาดทันที เอกสารหนึ่งฉบับมีข้อมูล 20 ถึง 30 ข้อ แต่ภาพหนึ่งใบรับได้จริงราว 5 ถึง 6 ข้อ คือตัดให้เหลือประมาณ 30% ของเนื้อหาเดิม ภาพมีหน้าที่พาคนเข้าไปหาเอกสาร ไม่ใช่แทนเอกสาร

**กติกาการถาม** คำตอบส่วนใหญ่อยู่ในบริบทงานอยู่แล้ว ทั้งเอกสารต้นทาง บริบทของดีล ผู้ชมที่รู้จากงานก่อนหน้า และรูปแบบผลลัพธ์ที่งานกำหนดมา ให้ตอบร่างทุกข้อเองจากบริบทก่อน แล้วเสนอเป็นร่างโจทย์ชุดเดียวให้ user ยืนยันหรือแก้ พร้อมระบุชัดว่าข้อใดอนุมานเอง และถามตรง ๆ เฉพาะข้อที่บริบทไม่มีคำตอบจริง ๆ

❌ "ก่อนออกแบบ ขอถาม 5 ข้อ: 1. คนอ่านควรจำอะไร 2. คนอ่านมีคำถามอะไร ..." — โยนงานคิดกลับไปให้ user ทั้งชุด
✅ "ร่างโจทย์จากบริบทงาน: คนอ่านคือประธานเจ้าหน้าที่บริหารฝ่ายการเงิน ควรจำกลับไปว่าทางเลือก ข ถูกกว่า 28% ในสามปี · คำถามในหัวคือจะเลือกอันไหน จึงใช้โครงเปรียบเทียบ · ใช้ฉายในห้องประชุมสัดส่วน 16:9 · ตัวเลขใหญ่สุดคือส่วนต่างสามปี — สองข้อนี้ผมอนุมานจากข้อเสนอ ท่านยืนยันหรือแก้ได้ ส่วนที่ผมไม่รู้จริงคือข้อเดียวที่ถามนี้"

**คำถามตั้งโจทย์ 5 ข้อ**

1. **คนที่เห็นภาพนี้ควรจำอะไรกลับไปหนึ่งอย่าง** — ตอบไม่ได้แปลว่ายังเริ่มไม่ได้ ภาพจะรกแน่นอน
2. **คนอ่านมีคำถามอะไรอยู่ในหัว** — คำตอบชี้โครงภาพโดยตรงตามตารางข้างล่าง ไม่ใช่ดูจากหน้าตาเอกสารต้นทาง
3. **ภาพนี้ใช้ที่ไหน** — สไลด์ 16:9 · พิมพ์กระดาษ A4 แนวตั้งสัดส่วน 2:3 · ส่งในแชทสัดส่วน 1:1 · หรือหน้าเว็บ ซึ่งกำหนดขนาดและระยะการอ่าน
4. **อะไรต้องใหญ่ที่สุด** — ลำดับสายตาคือลำดับความสำคัญ ต้องสั่งเองว่าอะไรใหญ่ อะไรรอง อะไรเล็ก ไม่ปล่อยให้จัดตามความสวยงาม
5. **ตัวเลขแต่ละตัวเทียบกับอะไร** — คำว่า "โต 18%" ลอย ๆ อ่านไม่ออกว่ามากหรือน้อย ทุกตัวเลขต้องมีตัวเทียบกำกับ

| คำถามในหัวคนอ่าน | โครงที่ใช้ | กติกาเฉพาะโครง |
|---|---|---|
| ฉันควรเลือกอันไหน | **เปรียบเทียบ** คอลัมน์เท่ากัน | ใช้เกณฑ์เดียวกันทุกคอลัมน์ · เกณฑ์ที่มีข้อมูลไม่ครบทุกฝั่งให้ตัดแถวทิ้ง เพราะช่องว่างทำให้ตัวเลือกหนึ่งดูแย่เกินจริง |
| ฉันต้องทำอะไรก่อน | **ลำดับขั้นตอน** | เส้นทางเดียวจากบนลงล่าง แยกได้ไม่เกินสองทาง · ตัดขั้นที่ไม่ใช่หน้าที่ของคนอ่านออกให้หมด |
| อะไรเป็นก้อนใหญ่ | **สัดส่วน** | พาดหัวคือข้อสรุป ไม่ใช่ชื่อรายงาน · ตัวเลขในภาพไม่เกิน 5 ตัว |
| มันเปลี่ยนไปอย่างไร | **ก่อนและหลัง** | สองฝั่งใช้หน่วยเดียวกันและมีรายการเท่ากัน · รายการที่แย่ลงต้องแสดงด้วย ภาพที่ดีขึ้นทุกข้ออ่านแล้วเป็นโฆษณาทันที |
| เกิดอะไรขึ้นเมื่อไหร่ | **ไทม์ไลน์** | ระยะห่างระหว่างจุดต้องสัมพันธ์กับเวลาจริง ไม่ใช่เท่ากันหมด · ไม่เกิน 7 จุด |

**หลักสากลที่ใช้กับทุกโครง** สัดส่วนหมึกที่เป็นข้อมูลต้องมากกว่าหมึกที่เป็นของตกแต่ง จึงตัดเงา ภาพสามมิติ การไล่เฉดเพื่อประดับ เส้นกรอบ และพื้นผิว ออกก่อนเสมอ ซึ่งสอดคล้องกับด่านหัวข้อ 4.8 · ความซื่อตรงของภาพคือแกนไม่บิด สเกลสม่ำเสมอ และพื้นที่ในภาพแปรผันตรงกับตัวเลขจริง ภาพที่สวยแต่บิดสัดส่วนเสียหายกว่าภาพธรรมดา · ลำดับขนาดคุมสายตาโดยพาดหัวใหญ่กว่าหัวข้อรอง ใหญ่กว่าเนื้อความ ใหญ่กว่าป้ายกำกับ ในสัดส่วนราว 2.5 ต่อ 1.5 ต่อ 1 ต่อ 0.8 และตัวเลขสำคัญเด่นกว่าข้อความรอบข้างเสมอ · ตัวเลขมาจากแหล่งจริงเท่านั้น และต้องตรวจย้อนกลับทุกภาพก่อนใช้ โดยไล่ทุกตัวเลขว่ามาจากส่วนใดของต้นฉบับ ตัวใดคำนวณเอง ตัวใดหาที่มาไม่ได้ ขั้นนี้ข้ามไม่ได้ เพราะตัวเลขผิดตัวเดียวในห้องประชุมเสียหายกว่าภาพไม่สวย

**กติกาไอคอน** (1) ค้นคลังและเปลี่ยนสีก่อนสร้างใหม่ตามหัวข้อ 4.7 สัญลักษณ์สากลมาก่อนสัญลักษณ์ที่คิดขึ้นใหม่ (2) ใช้ชุดเดียวทั้งเอกสาร คือกริดเดียวกัน (ฐาน 24 พิกเซล เผื่อขอบ 2 พิกเซล) น้ำหนักเส้นเดียวกัน และเลือกอย่างใดอย่างหนึ่งระหว่างแบบเส้นกับแบบทึบทั้งชุด เพราะไอคอนต่างสไตล์ปนกันคือร่องรอยตามหัวข้อ 4.8 (3) ทดสอบที่ขนาดใช้จริง ไอคอนต้องอ่านออกที่ขนาดเล็กที่สุดที่จะปรากฏ รายละเอียดที่หายตอนย่อให้ตัดออก (4) ไอคอนทุกตัวต้องสื่อความหมาย ตัวที่ประดับเฉย ๆ ให้ตัดตามหลักสัดส่วนหมึกที่เป็นข้อมูล และไม่ใช้ emoji แทนไอคอน

| รูปแบบผลลัพธ์ | ข้อกำหนดเฉพาะ |
|---|---|
| **PPTX** | วาดเป็นรูปทรงและกล่องข้อความจริงตามวินัยการสร้างไฟล์ เพื่อให้แก้ไขและค้นหาข้อความได้ · ภาพที่สร้างด้วย AI จะมีตัวหนังสือไทยฝังอยู่ไม่ได้ · ฟอนต์ตามรางในหัวข้อ 4.6 และตั้งครบทุกช่องรวมช่องอักษรซับซ้อน |
| **ภาพอินโฟกราฟิกที่สร้างด้วย AI** | ภาพเป็นฉากและองค์ประกอบเท่านั้น ตัวหนังสือทั้งหมดวางเป็นชั้นข้อความจริงทับลงไป · การแก้ทีละจุดต้องสั่งว่าส่วนที่เหลือคงเดิมทุกอย่าง แล้วเทียบภาพก่อนและหลังทุกครั้ง · คำบรรยายตัวเล็กเสี่ยงเพี้ยน ข้อความสำคัญจึงไม่ปล่อยให้เล็ก |

**ลำดับการทำงานจริง** ตอบร่างโจทย์ 5 ข้อเองจากบริบท แล้วรวมเข้ากับแผนภาพรายหน้าของหัวข้อ 4.4 ขั้นที่ 4 เสนอ user ยืนยันครั้งเดียว (ถามตรงเฉพาะข้อที่ไม่รู้) แล้วทำขั้นตัดพร้อมแจ้งสิ่งที่ตัดและเหตุผล แล้วเสนอโครงสองทางพร้อมข้อเสียให้ user เลือก แล้วเขียนลง design spec ให้ครบทั้งโครง ลำดับขนาด ตัวเทียบของตัวเลข ชุดไอคอน และรูปแบบผลลัพธ์ แล้วจึงสร้างไฟล์ แล้วตรวจตัวเลขย้อนกลับ แล้วส่งอริสตรวจในด่านหัวข้อ 4.8 และมิติ D7

### 4.11.1 เครื่องหมายยืนยันการตั้งโจทย์ `ICE_DESIGN=briefed`

**เครื่องหมายนี้คืออะไร** ข้อความ `ICE_DESIGN=briefed` ที่เติมไว้หน้าคำสั่งสร้างไฟล์นำเสนอ เป็นคำประกาศว่าผู้สร้างทำ DESIGN BRIEF ตามหัวข้อ 4.11 ครบแล้วก่อนลงมือวาด หัวข้อนี้เป็นบ้านเดียวของเครื่องหมายนี้ ไฟล์อื่นที่เอ่ยถึงให้ชี้กลับมาที่นี่

**ทำไมต้องมี** ตัวตรวจก่อนสร้างไฟล์จะปฏิเสธคำสั่งสร้างไฟล์นำเสนอที่ไม่มีเครื่องหมายนี้ ผู้ที่ต้องการสร้างไฟล์จึงต้องเปิดอ่านหัวข้อ 4.11 ก่อนเสมอ ซึ่งทำให้ได้ความรู้เรื่องการออกแบบติดมือไปด้วย เหตุผลที่ต้องบังคับด้วยเครื่องมือแทนการเขียนกฎเตือน คือการตรวจงานจริงสี่ครั้งติดต่อกันในเดือนสิงหาคม 2026 พบว่าสกิลออกแบบไม่เคยถูกเปิดอ่านเลยแม้แต่ครั้งเดียวทั้งที่มีกฎสั่งไว้แล้ว ผลคือ user รายงานว่างานที่ได้สีไม่สวยและเหมือนไม่ได้ใช้แม่แบบ

**ใช้เมื่อไหร่** ทุกคำสั่งที่สร้างหรือแก้ไฟล์นำเสนอ `.pptx` และงานที่ต้องวาดอินโฟกราฟิกหรือไอคอนทุกรูปแบบผลลัพธ์

❌ `ICE_BUILD=pipeline python3 build_deck.py` — ตัวตรวจปฏิเสธ เพราะไม่มีคำประกาศว่าผ่านการตั้งโจทย์ออกแบบแล้ว
✅ `ICE_BUILD=pipeline ICE_DESIGN=briefed python3 build_deck.py` — ประกาศหลังตอบชุดคำถามตั้งโจทย์ในหัวข้อ 4.11 และเขียนผลลง design spec เรียบร้อยแล้ว

**ห้ามประกาศเครื่องหมายนี้โดยไม่ได้ทำจริง** เพราะเท่ากับข้ามขั้นตอนคิดแล้วไปวาดเลย ซึ่งเป็นต้นเหตุของงานที่ต้องแก้วนหลายรอบ

## 5.5 รายการฟอนต์ที่อนุมัติและตารางประกอบ

รายการฟอนต์ที่อนุมัติแบ่งตามผู้ฟัง 4 ระดับ (T1 ถึง T4) พร้อมข้อแลกเปลี่ยนรายตัว ลำดับการเลือกตามผู้ฟัง ฟอนต์ค่าเริ่มต้นของแม่แบบทั้ง 8 ชุด คู่ฟอนต์ที่ไม่จับคู่กัน และวิธีทดสอบความสูงตัวอักษรด้วยสายตา **อยู่ที่ `references/font-selection.md`** ใช้ตารางเหล่านั้นเมื่อแม่แบบไม่ระบุฟอนต์ชัดเจนหรือเมื่อต้องเขียนคู่มือฟอนต์เฉพาะงาน · นโยบายที่ใช้เป็นค่าตั้งต้นของงานปัจจุบันคือนโยบาย 2 รางในหัวข้อ 4.6

กฎที่ต้องถือทุกงานสองภาษาแม้ไม่เปิดไฟล์ปลายทาง คือคู่มือการออกแบบต้องระบุทั้งฟอนต์ละตินและฟอนต์อักษรซับซ้อนเสมอ (PPTX ใช้ช่อง `latin` และ `cs` · Word ใช้ `w:ascii` และ `w:cs`) เพราะถ้าเว้นช่องอักษรซับซ้อนไว้ ระบบ Windows จะเปลี่ยนไปใช้ Browallia New หรือ Cordia New เอง ทำให้หน้าตาเอกสารเสีย · ตัวอย่างการเขียนอยู่ในไฟล์ปลายทางหัวข้อ 6

### 5.5.1 การเลือกฟอนต์ที่ฝังลงไฟล์ได้ — แหล่งอ้างอิงเดียวของทั้งทีม

หัวข้อนี้เป็นเจ้าของเรื่องการเลือกฟอนต์สำหรับงานที่ต้องฝังฟอนต์ สกิล `b2b-presentation-creator` หัวข้อ 5.1 ชี้มาที่นี่แทนการเขียนกฎซ้ำ แก้ที่นี่แล้วปลายทางได้ตาม **ตารางผลตรวจค่า fsType ของฟอนต์ 7 ตัว กฎสามข้อของฟอนต์ที่ฝังได้ และคู่ฟอนต์ที่ฝังได้ถูกลิขสิทธิ์ อยู่ที่ `references/font-selection.md` หัวข้อ 2** สรุปสั้นที่ใช้ตัดสินได้ทันทีคือ ฟอนต์ที่จะฝังต้องเป็นแบบคงที่ (ฟอนต์แบบแปรผันต้องแปลงก่อน) ค่า fsType ต้องไม่ใช่ 0x0002 ที่ปิดการฝัง และต้องผ่านการทำให้เป็นมาตรฐานด้วย fontTools หนึ่งรอบ

การฝังฟอนต์ลงไฟล์จริงเป็นงานของ `deliverable-gen` ด้วย `_lib/embed_fonts_pptx.py` ไม่ใช่งานของสกิลนี้ สกิลนี้มีหน้าที่เลือกฟอนต์ให้ถูกแล้วส่ง spec ต่อ

## 5.6 งานที่ออกเป็น HTML

เมื่อผลลัพธ์เป็น deck แบบ HTML สกิลนี้ยังเป็นผู้ป้อนคู่มือการออกแบบเหมือนเดิม แต่ส่งออกเป็นตัวแปร CSS ให้ `b2b-presentation-creator` และสคริปต์ `scripts/build_html.py` นำไปสร้าง สกิลนี้ไม่สร้างไฟล์เอง · รายละเอียดครบอยู่ที่ `references/html-styling-export.md`

สิ่งที่สกิลนี้ทำให้งาน HTML มีสี่อย่าง (1) แปลงธีมของแม่แบบทั้ง 8 ชุดเป็นตัวแปร CSS ได้แก่ `--accent` `--stage-bg` และชุดสีของหน้า ตามตารางในไฟล์ปลายทางหัวข้อ 1 (2) จับคู่ฟอนต์ที่หัวข้อ 5.5.1 เลือกไว้แล้วกับฟอนต์ที่ใช้บนเว็บได้ เช่น Sukhumvit Set ใช้ Kanit แทนบนเว็บ ส่วน Sarabun IBM Plex Sans Thai และ Kanit มีให้ใช้บน Google Fonts อยู่แล้ว โดยหัวข้อ 5.5.1 ยังเป็นผู้เลือกฟอนต์ หัวข้อนี้เพียงเพิ่มตัวสำรองสำหรับเว็บ (3) วางฟอนต์ไทยไว้หน้าฟอนต์ละตินในรายการฟอนต์ของ CSS เสมอ เช่น `'Sarabun','Open Sans'` ซึ่งทำหน้าที่แทนการตั้งช่อง latin กับ cs ของ PPTX (4) กำหนดเวทีขนาดคงที่สัดส่วน 16:9 ที่ 1920×1080 แล้วย่อขยายตามจอ พร้อมค่าความต่างของสีอย่างน้อย 4.5 ต่อ 1 และตั้งเป้าที่ 7 ต่อ 1 เมื่อฉายด้วยโปรเจกเตอร์

วินัยการออกแบบของ deck แบบ HTML ใช้ `references/design-principles.md` ซึ่งเป็นกฎ 20 ข้อที่ใช้ได้กับทุกรูปแบบผลลัพธ์รวมถึง `.pptx` ด้วย
