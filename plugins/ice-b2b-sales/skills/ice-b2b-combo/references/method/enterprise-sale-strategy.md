# Method — Enterprise Sale Strategy (Segment Playbook)

> **Coverage:** playbook ตาม segment ลูกค้า 3 แบบ (ภาครัฐ/SOE · Large Enterprise · SME+/Mid-market) — decision-maker, sales cycle, win-rate, ความเร่ง, การ right-size product, และ battlecard คู่แข่งที่ต่างกันตาม segment.
> **Sale stage:** ใช้ตั้งแต่ Qualify → Account Plan → Proposal → Negotiate (เลือก segment ก่อน แล้วปรับวิธีเล่นทั้งดีล).
> **เอกลักษณ์ไฟล์นี้:** "ลูกค้าแต่ละ segment ซื้อไม่เหมือนกัน" — ส่วนกลาง (qualify/why/กรอบคิด/ภาษาไทย) ชี้ไป `_shared/`.

## 0. เลือก segment ก่อน (decision gate)

ก่อนวางกลยุทธ์ดีล ระบุ segment — มันกำหนดทั้ง cycle, decision-maker, ความเร่ง, และ tone:

| สัญญาณ | Segment | ไปอ่านหัวข้อ |
|---|---|---|
| หน่วยงานราชการ · มหาวิทยาลัยรัฐ · e-bidding · TOR · ปีงบ ต.ค.–ก.ย. | **ภาครัฐ** | §1 |
| รัฐวิสาหกิจ (มีงบจากรายได้เอง · board approve) | **SOE** | §1.6 |
| บริษัทใน SET · MNC · กลุ่มทุน/conglomerate | **Large Enterprise** | §2 |
| รายได้ ~100M–5B บาท · ธุรกิจครอบครัว · เจ้าของตัดสินเอง | **SME+ / Mid-market** | §3 |

ไม่ชัด segment = ถามก่อน (อย่าเดา — playbook ผิด segment = เสียดีล). ภาษา/มารยาท/SOE overlay → ดู `references/_shared/thai-calibration.md`.

## 1. ภาครัฐ (Government / Public Sector)

### 1.1 จุดต่างที่กำหนดทุกอย่าง
- **คนเขียน TOR = คนชี้ผู้ชนะ** (โดยปริยาย) — สร้างความเข้าใจกับทีม TOR **6–12 เดือนก่อน** ประกาศ.
- ผูกกับ **ปีงบประมาณ** — การบรรจุงบเกิด ต.ค.–ธ.ค. สำหรับปีถัดไป → engage **12–18 เดือนล่วงหน้า**.
- Paper Process + Decision Process ผูกระเบียบจัดซื้อ — เป็นหัวใจของ qualify (ดู `_shared/meddpicc.md` ตัว P/D).

### 1.2 จังหวะเข้าทำ (timeline-led)
| ช่วงก่อนประกาศ | สิ่งที่ทำ |
|---|---|
| 12–18 เดือน | ติดตามแผนแม่บท/แผนดิจิทัล · จับ project ที่จะเกิด · สร้างสัมพันธ์ระดับ CIO/ผู้กำหนดทิศ |
| 6–12 เดือน | **ให้ความรู้** (สัมมนา/study visit/feasibility) — educate ให้ TOR สอดคล้องจุดแข็งเรา **โดยไม่เขียน TOR ให้เขา** |
| 1–3 เดือน | เฝ้า e-GP รายวัน · วิเคราะห์ TOR vs ขีดความสามารถ · ฟอร์ม JV/consortium ถ้าจำเป็น · เตรียมเอกสารคุณสมบัติ |
| ยื่นซอง | ข้อเสนอเทคนิค + ราคา (ดู §1.4) |
| หลังได้งาน | ยึด scope/timeline เป๊ะ · รายงาน steering · เอกสารภาษาไทยให้กรรมการตรวจรับ |

### 1.3 กฎเหล็กภาครัฐ
- **อย่าเขียน TOR ให้ลูกค้า** — ให้ความรู้จนเขาเขียนเองแล้วบังเอิญ fit เรา.
- ตอบ TOR ให้ครบทุกข้อ — ขาดข้อเดียว = ตัดสิทธิ์อัตโนมัติ (checklist ทุกข้อ).
- ห้าม over-promise — สัญญารัฐมีบทปรับ/ขึ้นบัญชีดำ.
- เอกสารภาษาไทยมืออาชีพ = คะแนนเทคนิค (ดู `_shared/thai-calibration.md`).

### 1.4 โครงข้อเสนอภาครัฐ (มาตรฐานไทย)
```
ส่วนที่ 1 — ข้อเสนอเทคนิค
  1.1 ความเข้าใจขอบเขตงาน (Understanding of TOR)
  1.2 แนวทาง/วิธีดำเนินงาน (Methodology)
  1.3 แผนงาน/timeline
  1.4 ทีมงาน + CV
  1.5 ประสบการณ์ + reference
ส่วนที่ 2 — ข้อเสนอราคา (ซองปิดผนึก)
  2.1 ราคารวม · 2.2 รายละเอียดค่าใช้จ่าย · 2.3 เงื่อนไขชำระเงิน
```

### 1.5 โมเดลให้คะแนนราคา
- **ราคาประเมินต่ำสุด** — เทคนิคต้องผ่านเกณฑ์ขั้นต่ำ (มัก 80%) แล้วราคาต่ำสุดในกลุ่มที่ผ่านชนะ → optimize เทคนิคพร้อมราคาแข่งได้.
- **คะแนนรวมถ่วงน้ำหนัก** — เทคนิค 60–80% : ราคา 20–40% → เน้นสร้างความต่างเชิงเทคนิค.
- ราคาต้องสมเหตุผล (สตง.ตรวจ) · ต้นทุนโปร่งใส · ระวังราคา maintenance หลายปี (รายได้ recurring).

### 1.6 SOE (รัฐวิสาหกิจ)
ต่างจากราชการปกติ — เล่นเหมือน Large Enterprise + overlay compliance:
- อำนาจจัดซื้ออิสระกว่า · งบจากรายได้เอง · มักมีบริษัทลูกด้าน IT.
- ลงทุนก้อนใหญ่ต้อง **board approve** → สร้างสัมพันธ์ทั้งระดับบริหารและบอร์ด.
- เข้าใจ digital roadmap ของแต่ละ SOE · **จับมือบริษัทลูก IT ของเขา อย่าไปแข่ง**.

### 1.7 กับดักภาครัฐ
| กับดัก | ผล | กันยังไง |
|---|---|---|
| เข้าช้า | TOR เอียงคู่แข่ง | เริ่ม 12–18 เดือนก่อน |
| แข่งราคาล้วน | margin หด | shape TOR ให้ประเมินที่ value |
| เอกสารไม่ครบ | ตัดสิทธิ์ | checklist ทุกข้อ TOR |
| over-promise | ส่งมอบล้ม/blacklist | honest เรื่อง capability |
| ไม่มี local partner | ยื่นไม่ได้ | หา JV แต่เนิ่น ๆ |
| ไม่เข้าใจปีงบ | พลาดหน้าต่างงบ | align กับรอบ ต.ค.–ก.ย. |

> รายละเอียดระเบียบจัดซื้อ/e-GP/TOR → ดู `references/domain/govt-egp.md` · งบประมาณ → `references/domain/govt-gfmis.md`.

## 2. Large Enterprise (SET / MNC / Conglomerate)

### 2.1 จุดต่างที่กำหนดทุกอย่าง
- **Budget authority แยกระดับ** — CIO/CFO อนุมัติ < ~50M · CEO/Board > ~50M.
- Cycle 4–12 เดือน · ประเมินแบบ RFP มีคะแนน · POC/pilot บ่อย.
- ตัดสินใจหลายชั้น — ต้อง **multi-thread** (อย่าพึ่งสัมพันธ์เดียว).

### 2.2 Dual-Track สำหรับ conglomerate
เล่น 2 ระดับเสมอ:
1. **Group level** — strategic partnership, มาตรฐาน platform, volume licensing.
2. **BU level** — โจทย์เฉพาะหน่วย, quick win, proof of value.

MNC: หา "จุดตัดสินจริง" — ถ้าเป็น **global mandate** ("ทั้งกลุ่มใช้ X") ให้โฟกัสความเป็นเลิศของ local implementation แทนที่จะสู้เรื่องเลือก product.

### 2.3 Account Plan (โครง)
```
1. ภาพรวม account — ธุรกิจ/รายได้/ทิศกลยุทธ์/IT landscape ปัจจุบัน/โจทย์
2. Relationship map — sponsor · technical champion · economic buyer · blocker · coach
3. โอกาส — project ที่รู้ · latent need · trigger event (M&A/CEO ใหม่/IPO/กฎใหม่) · ภัยคู่แข่ง
4. Win strategy — value prop เฉพาะ account · positioning · proof point · โครงดีล
5. Action plan — 30 วัน / 90 วัน / 12 เดือน
```
> Champion/economic buyer/competition = ตัวใน `_shared/meddpicc.md` · value prop narrative → `_shared/why-stack.md`.

### 2.4 Multi-Threading (จับคู่ระดับ)
| ฝั่งเรา | ฝั่งลูกค้า |
|---|---|
| ผู้บริหารระดับสูง | CEO/MD |
| Sales lead | CFO/CIO |
| Solution architect | IT Director / Enterprise Architect |
| Project manager | Business process owner |
| Account manager | Procurement |

ไต่ระดับความไว้ใจ: **Vendor (ราคา) → Advisor (value) → Partner (outcome) → Strategic ally (co-create)**.

### 2.5 องค์ประกอบดีลใหญ่ (TCV)
```
SOFTWARE/LICENSE — SaaS subscription · perpetual+maintenance · cloud infra
IMPLEMENTATION — advisory · config/dev · data migration · integration · testing · training+change mgmt
MANAGED SERVICES/AMS — support L1-L3 · enhancement · managed cloud ops
OPTIONAL — POC/innovation lab · process assessment · transformation advisory
```
โครงสร้าง win-win: phased (ลด cost ปี 1) · success-based (ผูกค่าธรรมเนียมกับ outcome) · volume commitment · reference agreement (ลดราคาแลกเป็น reference).

### 2.6 แทนที่ ERP เดิม (competitive displacement)
ดีลยากที่สุด — เล่นเป็นชั้น:
1. **อย่าโจมตีของเดิมตรง ๆ** — ชี้ช่องว่างที่ของเดิมเติมไม่ได้ (กฎใหม่/cloud/analytics) · positioning แบบเสริม.
2. **Land ด้วย wedge** — เริ่มจาก module ที่ของเดิมอ่อน · EPM/Planning เป็น wedge ที่ดีสุด (วางทับ ERP อะไรก็ได้) · HR/Procurement cloud ก็ได้.
3. **ขยายจากจุดแข็ง** — ส่งมอบ wedge ให้ดีเยี่ยม สร้าง advocate ภายใน รอรอบเปลี่ยน ERP (ทุก 7–12 ปี).
4. **เสนอ platform เต็ม** เมื่อพร้อม — ใช้สัมพันธ์ + track record ที่พิสูจน์แล้ว.

### 2.7 Industry quick-fit
| อุตสาหกรรม | hot topic | ERP ที่มัก fit |
|---|---|---|
| Manufacturing | Industry 4.0, supply chain | Oracle SCM, SAP S/4, Infor |
| Banking/Finance | IFRS9/TFRS9, digital | Oracle ERP+EPM |
| Retail | omnichannel | Oracle Cloud, NetSuite |
| Energy | ESG, asset, carbon | SAP, Oracle ERP |
| Healthcare | compliance, patient exp | Oracle Cloud |
| Conglomerate HQ | group consolidation, GRC | Oracle EPM |

## 3. SME+ / Mid-market (Normal Enterprise)

### 3.1 จุดต่างที่กำหนดทุกอย่าง
- **เจ้าของ = คนตัดสิน** — ทุกอย่างเริ่มและจบที่เจ้าของ → เข้าถึงเจ้าของให้เร็ว สร้างความไว้ใจส่วนตัว.
- Cycle สั้น **2–4 เดือน** (เทียบ 6–18 เดือนของรายใหญ่) → **ความเร็วคือความได้เปรียบ**.
- **The Auditor Effect** — ผู้สอบบัญชีคือที่ปรึกษาที่ลูกค้า mid-market ไว้ใจที่สุด · ถ้าผู้สอบบัญชีแนะนำระบบ เจ้าของฟัง → สร้าง referral กับสำนักบัญชี.

### 3.2 Trigger ที่ทำให้ลงทุน
growth pain (manual ตามไม่ทัน) · compliance (e-Tax/Transfer Pricing/BOI/PDPA) · succession (รุ่นใหม่อยากได้ระบบทันสมัย) · ข้อกำหนด export · ผลตรวจสอบบัญชี · แรงกดดันคู่แข่ง · M&A.

### 3.3 Velocity cycle
```
LEAD → QUALIFY → DEMO → PROPOSE → NEGOTIATE → CLOSE → IMPLEMENT
1-2wk   1-2wk    1-2wk   1-2wk      1-4wk      1wk     3-9mo
รวม ~2–4 เดือน
```

### 3.4 Qualify เร็ว (เกณฑ์ go/no-go สำหรับ SME)
| เกณฑ์ | go/no-go |
|---|---|
| งบ/ความพร้อมจ่าย | ขั้นต่ำ ~3M บาทสำหรับ ERP พื้นฐาน |
| เข้าถึงเจ้าของ | ต้องถึงเจ้าของภายใน 2 นัด |
| pain จริง | บอกปัญหาเฉพาะได้ |
| timeline | ภายใน 12 เดือน = ไล่จริงจัง |
| ความซับซ้อน | right-size solution ตามความซับซ้อน |
> qualify เต็มรูป 8 องค์ประกอบ → `_shared/meddpicc.md` (สำหรับ SME ใช้แบบ light: M + Economic Buyer + Pain + Timeline พอเริ่ม).

### 3.5 Demo = ช่วงตัดสิน
- ไม่เกิน 2 ชม. (สมาธิเจ้าของจำกัด) · ใช้ scenario อุตสาหกรรม **ของเขา** ไม่ใช่ data demo กลาง.
- โฟกัส pain ที่เขาพูดใน discovery · โชว์ financial close / reporting / dashboard (ทีมบัญชีชอบ) · มี mobile (เจ้าของเช็คมือถือ).
- ปิดด้วย: "ถ้าเราส่งมอบสิ่งนี้ได้ใน 4–6 เดือน มันแก้ปัญหาท่านไหมครับ"
- **มีคนนำเสนอภาษาไทยเสมอ** — demo อังกฤษล้วนเสียลูกค้า mid-market.

### 3.6 Right-size product ตาม profile
| โปรไฟล์บริษัท | solution ที่มัก fit | เพราะ |
|---|---|---|
| 50–200 คน single entity | NetSuite, SAP B1, Odoo, MS BC | ราคาเหมาะ deploy เร็ว |
| 200–500 คน multi-entity | NetSuite, Oracle Cloud, MS F&O | scale + consolidation |
| 500–2000 คน ซับซ้อน | Oracle Cloud ERP, SAP S/4, MS F&O | enterprise-grade |
| เน้น manufacturing | SAP B1, Oracle SCM, Infor | MRP, shop floor |
| service/project | NetSuite, MS F&O, Oracle | project accounting |
| distribution/trading | SAP B1, NetSuite, Odoo | inventory, multi-warehouse |
| โตเร็ว/tech | NetSuite, Odoo | cloud-native |
> รายละเอียด product → `references/product/*.md`.

### 3.7 Pricing สำหรับเจ้าของ-ผู้บริหาร
- **โชว์ value รวมก่อน แล้วค่อยบอกราคา** — อย่านำด้วยราคา.
- เทียบกับต้นทุน current state ("ตอนนี้เสียกับ manual ปีละ X") · อ้างบริษัทขนาดใกล้กัน ("บริษัทขนาดท่านมักลงทุน Y").
- early-decision incentive ("เซ็นก่อนสิ้นไตรมาส ลด Z%") · **อย่าลดราคาฟรี** — แลกกับ reference/timeline/scope.
- 3 โมเดล: all-inclusive package (เจ้าของอนุมัติง่าย) · subscription (ลด upfront, OpEx) · phased (60/25/15 พิสูจน์ value ก่อน commit เต็ม).
> ราคา/payback ต้องอิงตัวเลขลูกค้า — กุ ROI = อันตราย (ดู `_shared/why-stack.md` Why Invest + `_shared/frameworks.md` ROI frame).

### 3.8 Channel & referral flywheel
- **สำนักบัญชี/auditor** — formalize referral · **ที่ปรึกษาธุรกิจ** — co-propose · **ธนาคาร** — โครงการ digital transformation lending · **vendor (Oracle/SAP/MS partner)** — co-sell ใช้ lead เขา.
- ขอ referral ที่ milestone (go-live / 6 เดือน / 1 ปี) · จัด user group · ทำ case study ร่วม.
- ช่องทางไทย: Line OA (เร็วกว่า email) · งานขอบคุณลูกค้าประจำปี · roadshow ภูมิภาค (EEC/เหนือ/ใต้).

## 4. Solution Selling — 5 Phase (ใช้ได้ทุก segment)

ปรับความลึกตาม segment (ภาครัฐ/Large = เต็ม · SME = เร่ง):

| Phase | สาระ | หัวใจ |
|---|---|---|
| **1 DISCOVER** | เข้าใจลูกค้าลึก · power map stakeholder · ถาม situation→problem→implication→need-payoff | ห้ามข้าม |
| **2 CONSULT** | วางตัวเป็น advisor ไม่ใช่ vendor · maturity assessment · transformation roadmap (quick win→foundation→optimize→innovate) | educate ก่อนขาย |
| **3 ARCHITECT** | ออกแบบรอบ **business outcome** ไม่ใช่ feature (ดู §4.1) | outcome-first |
| **4 PARTNER** | โครงดีล win-win · ราคาที่ value ไม่ race-to-bottom · phased ลดความเสี่ยง | mutual benefit |
| **5 SUSTAIN** | ส่งมอบดี → trust → reference → expand · account growth ปีต่อปี | trust compound |

### 4.1 Outcome ไม่ใช่ feature (ตัวอย่าง re-frame)
| ลูกค้าพูด | อย่าขาย | ขาย |
|---|---|---|
| "อยากได้ ERP ใหม่" | list module ERP | finance transformation + insight real-time |
| "รายงานช้า" | feature EPM | ปิดงบเร็วขึ้น 70% / decision velocity |
| "งาน manual เยอะ" | feature automation | คนไปโฟกัสงานเชิงกลยุทธ์ |
| "โตเร็ว" | scalable architecture | platform พร้อมโต ไม่ถ่วงธุรกิจ |

> โครง narrative "ทำไมต้องซื้อ" (Why Change/Now/Us/Invest/Stay) → `_shared/why-stack.md`. กรอบจัดโครงคิด (MECE/Pyramid/value-chain/ROI) → `_shared/frameworks.md` (ใช้ในใจ — ผลงานเป็นภาษาธุรกิจ ไม่ name-drop).

## 5. Objection Handling (ไทย, ทุก segment)

| ข้อโต้แย้ง | reframe |
|---|---|
| "แพงเกินไป" | "ต้นทุนของการ **ไม่** เปลี่ยนคือเท่าไหร่" + เทียบ TCO 5 ปี |
| "เรายังไม่พร้อม" | "นั่นแหละเหตุผลที่เราเริ่มที่ assessment ไม่ใช่ implement เลย" |
| "ระบบเก่ายังใช้ได้" | "ใช้ได้ ≠ แข่งได้ — อุตสาหกรรมท่านอีก 3 ปีจะอยู่ตรงไหน" |
| "เคยล้มเหลวมาแล้ว" | "หลายองค์กรเคย — มาวิเคราะห์ว่าทำไม แล้วออกแบบให้สำเร็จ" |

## 6. Competitive Battlecards (positioning, ไม่ใส่ในเอกสารลูกค้า)

| สถานการณ์ | จุดยืน |
|---|---|
| **Oracle vs SAP** | Oracle ชนะ cloud-native/innovation speed/financial depth · SAP ชนะ manufacturing breadth/installed base → วาง Oracle "future-ready" vs SAP "legacy transformation" |
| **Oracle vs Microsoft** | Oracle ชนะ finance/SCM ซับซ้อน · MS ชนะ ecosystem (Office/Teams/Azure) → ยอม MS เมื่อลูกค้าผูก Microsoft ลึก |
| **NetSuite vs SAP B1** | NetSuite ชนะ cloud-native/multi-subsidiary/UX · B1 ชนะ partner ecosystem/add-on ไทย → NetSuite สำหรับบริษัทโต multi-entity |
| **Any Enterprise ERP vs Odoo** | ERP ชนะ security/control/audit trail/compliance/support · Odoo ชนะ cost/flexibility → ชู ERP เมื่อมีข้อกำหนด regulatory/audit |
| **Any vs Status Quo** | วิเคราะห์ cost of inaction + แรงกดดัน peer/regulation (ดู `_shared/why-stack.md` Why Change/Now) |

**กฎ:** battlecard ใช้คิดกลยุทธ์ — **ไม่เขียนชื่อคู่แข่งโจมตีในเอกสารลูกค้า** · แสดง differentiation ผ่านคุณภาพ fit กับ pain เขา. รายละเอียด product → `references/product/*.md`.
