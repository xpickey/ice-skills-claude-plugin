# Context Discipline — จัดการ context เมื่องานยาว

> วินัยการจัดการ context window เมื่องานยาว/หลายรอบ — ไม่ให้บวมจนช้า แพง และเหลือที่คิดงานน้อยลง.
> หลักการนี้ปรับมาจาก compaction policy ของ `claude-tmux-compact` (MIT) — **เอาเฉพาะ "นโยบาย" (เมื่อไหร่/อย่างไร)
> ไม่เอากลไก tmux/shell** (อันนั้นผูกเครื่อง). ใช้ได้ทุกสภาพแวดล้อมที่มีคำสั่ง compact หรือสรุป-แล้วทำต่อ.

---

## ทำไมต้องมีวินัยนี้

ทุกอย่างที่อ่านเข้าไปกินพื้นที่ context (เหมือน RAM). งานขายที่ยาว (อ่าน TOR + 5 reference + สร้าง deck +
QA หลายรอบ) สะสม context จนเต็ม → ช้าลง, แพงขึ้น, และคุณภาพการคิดลดเพราะที่เหลือน้อย. การ compact คือการ
"สรุปแล้วทิ้งของหนักที่ไม่ต้องใช้แล้ว" — แต่มีต้นทุน (สร้าง summary + reset cache) จึงต้องทำเฉพาะตอนคุ้ม.

---

## Worth-It Check (compact เมื่อครบ 3 ข้อเท่านั้น)

ประเมิน **ท้ายทุกขั้นของ pipeline** เมื่องานยาว — ไม่ต้องรอ context เต็ม:

1. **SAFE** — งานสำคัญ flush ลงไฟล์แล้ว · ไม่มี gate/approval ค้าง · ไม่มีอะไรยังไม่บันทึกที่จะหาย.
2. **PAYOFF** — **ยังเหลืองานเยอะ และ** ขั้นถัดไปใช้ context น้อยกว่าที่แบกอยู่ตอนนี้มาก.
   → **ประเมิน PAYOFF ก่อนเสมอ:** ถ้าเป็นงานสุดท้าย/ไม่มีอะไรต่อ → **หยุด ไม่ compact** (SAFE อย่างเดียวไม่พอ).
3. **NO-THRASH** — ขั้นถัดไปจะไม่รีบอ่านสิ่งที่เพิ่ง drop กลับมาทันที (ไม่งั้นเสียเปล่า 2 รอบ).

ครบ 3 ข้อ **และมี next action ชัด** → สรุปเป็น keep set → compact → ทำต่อ.

---

## Keep Set = Pointers ไม่ใช่ Payload

หัวใจที่ทำให้ context ลดเยอะ (~80%) โดยไม่เสียงาน: **เก็บแค่ตัวชี้ ไม่เก็บเนื้อ.**

เก็บ:
```
focus       : กำลังทำอะไรอยู่ (1 บรรทัด)
next action : ขั้นถัดไปสำคัญสุด (1 อย่าง)
pointers    : path ของไฟล์ state/หลักฐาน · เลข opportunity · ตัวเลขชุด Context-Lock
```

**ไม่เก็บ:** เนื้อ TOR เต็ม, เนื้อ reference, draft ยาว ๆ — พวกนี้อ่านกลับจาก path เมื่อต้องใช้.
(path กินไม่กี่ token · ไฟล์ที่มันชี้กินเป็นพัน)

ตัวอย่าง keep set:
```
focus: ทำ proposal NetSuite ลูกค้า manufacturing — เขียน section ราคาเสร็จ
next action: เขียน section implementation timeline (3 phase)
pointers: Context-Lock ที่ <path> · TOR ที่ <path> · draft ที่ <path> · product/netsuite.md
```

## จำแนกขอบเขตเมื่อ context สูง (อย่า compact มั่ว)

context สูงไม่ได้แปลว่า "ต้อง compact ทุกกรณี" — จำแนกก่อน:

- **TERMINUS** (งานจบ ไม่มีอะไรต่อ) → **สรุปแล้วหยุด — ไม่ compact**. (compact ตอนจบ = เสีย token กับ summary
  ที่ไม่มีใครใช้)
- **CONTINUATION** (มีงานต่อชัด หรือผู้ใช้บอกทำต่อ) → **compact แล้วทำต่อ**. ลำดับ: ยืนยันว่ามีงานต่อ → compact → ทำ.
- **GREY ZONE** (มีแค่งาน optional/suggested) → **ถามผู้ใช้ก่อน** compact เฉพาะเมื่อยืนยัน.

**กฎ:** compact จะเกิดเฉพาะเมื่อมีงานต่อให้กลับเข้าไปทำ และตามด้วยการทำงานต่อเสมอ.

---

## สรุปสั้น (ติดตัวไว้)

> งานยาว → ท้ายแต่ละขั้นถาม "คุ้มจะ compact ไหม?" (SAFE+PAYOFF+NO-THRASH) ·
> ถ้าคุ้ม → เก็บแค่ focus+next-action+paths แล้วทำต่อ ·
> งานจบไม่มีต่อ → ไม่ compact แค่สรุป.
