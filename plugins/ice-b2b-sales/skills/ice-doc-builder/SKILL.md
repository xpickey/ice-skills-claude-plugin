# ice-doc-builder — วินัยการสร้างไฟล์เอกสารและไฟล์นำเสนอของทีม iCE

> **Version:** V02R01 | **Date:** 2026.09.05 | ประวัติรุ่นทั้งหมดอยู่ที่ `references/skill-changelog.md`
> **ไฟล์นี้ใช้ทำอะไร:** เป็นกติกาและลำดับงานของ "ขั้นสร้างไฟล์" ในสายงานเอกสารของทีม ตั้งแต่เงื่อนไขก่อนลงมือ เครื่องหมายหน้าคำสั่งสร้างไฟล์ วินัยฟอนต์ไทยกับอังกฤษ ด่านตรวจด้วยเครื่อง จนถึงการส่งผู้ตรวจคุณภาพ ผู้อ่านเดินจากหัวข้อ 0 ถึง 8 ตามลำดับได้โดยไม่ต้องเดา
> **ใครใช้:** ผู้ที่สร้างไฟล์เอง คือ session หลักที่สวมบทกัปตัน คิม หรือสมนึก และ agent ผู้สร้างไฟล์เบื้องหลัง (เจนนี่) · ไฟล์ทุกชิ้นที่สร้างต้องผ่านผู้ตรวจคุณภาพ (อริส) เสมอ สกิลนี้ไม่ใช่ใบผ่านการตรวจ
> **ขอบเขต:** ไฟล์ .pptx .docx .xlsx PDF และ HTML ทุกชิ้นที่ทีมสร้าง ทั้งที่ส่งลูกค้าและใช้ภายใน
> **เรื่องที่ไม่อยู่ในไฟล์นี้และอยู่ที่ใด:** กฎออกแบบ 6 ข้อของสไลด์ทุกชุด อยู่ที่ `~/.claude/skills/b2b-slide-designer/references/pptx-design-doctrine.md` · การเลือกแม่แบบ ชุดสี icon และชุดคำถามตั้งโจทย์ก่อนวาด (หัวข้อ 4.11) อยู่ที่สกิล `b2b-slide-designer` · ลำดับงานสร้างสไลด์ตั้งแต่รับโจทย์จนส่งมอบ อยู่ที่สกิล `b2b-presentation-creator` · กติกาภาษา อยู่ที่สกิล `ice-writing-register` · "งานประเภทไหนต้องโหลด skill ใดก่อนคิด" อยู่ที่ตารางเส้นทาง `~/.claude/hooks/skill-routing.yaml` เพียงแห่งเดียว
> **path ในไฟล์นี้:** path ที่ขึ้นต้นด้วย `references/` สัมพัทธ์กับโฟลเดอร์ของสกิลนี้คือ `~/.claude/skills/ice-doc-builder/` · สคริปต์ตรวจและสร้างทุกตัวเรียกด้วย path เต็ม `python3 ~/.claude/agents/_lib/<ชื่อสคริปต์>` · ข้อเท็จจริงที่เปลี่ยนได้เอง (ไลบรารีที่ติดตั้ง ฟอนต์บนเครื่อง) ให้ถามเครื่องมือตามคำสั่งที่ระบุ ไม่เชื่อข้อความในไฟล์นี้

## ลำดับงานทั้งหมด — เดินจากขั้นที่ 1 ถึงขั้นที่ 7 ตามลำดับ

```
1. ตรวจเงื่อนไขก่อน build (§0.1 ข้อ 0 ถึง 4 รวม 1b 1c · 6 · 8) → คำถามค้างเป็นศูนย์ · อ่านไฟล์รุ่นล่าสุดบนดิสก์แล้ว · โหลด skill ตามตารางเส้นทางแล้ว
2. เขียน content-spec และ design-spec ลงดิสก์ (§0.5) → ทุกหน้ามีช่องครบตามแม่แบบ · ชื่อไฟล์มีคำว่า spec
3. เขียน build script ลงดิสก์ (§0.1 ข้อ 3-4)       → ฟอนต์ดึงจาก font_policy.RAILS ไม่เขียนชื่อฟอนต์ตายตัว
4. รันด้วยเครื่องหมายที่ตรงบทบาท (§0.2)           → ICE_BUILD=pipeline + ICE_BASE=… (+ ICE_DESIGN=briefed สำหรับ .pptx และงานทุกฟอร์แมตที่มีภาพ)
5. บันทึกรุ่น V##R## แล้วยืนยันด้วย ls (§0.3)      → รุ่นก่อนหน้าย้ายเข้า _archive/ ในคำสั่งเดียวกัน
6. ตรวจด้วยเครื่องรอบเดียว (§6 และตาราง "ลำดับตรวจก่อนส่ง") → ผลเป็นตัวเลขจริง ไม่ใช่คำว่าผ่านลอย ๆ
7. ส่งอริสตรวจ แล้วแก้ตามรายการที่สรุปแล้วเท่านั้น (§0.4) → บันทึก R+1 · อริสตรวจส่วนต่างซ้ำ
```

## 0.1 เงื่อนไขก่อน build (ข้อ 0-4 · 6 · 8 ต้องครบจึงเริ่ม · ข้อ 5 ทำหลัง build · ข้อ 7 ใช้เมื่อ user เอ่ยชื่อแม่แบบ · ข้อ 9 ใช้เมื่อจะทำไฟล์ประกอบ)

**ลำดับงานเมื่อ "แก้ไฟล์ที่มีอยู่แล้ว" (สถานการณ์ที่พบบ่อยที่สุด):** (1) อ่านไฟล์จริงก่อนถาม — `ls` หารุ่นสูงสุดบนดิสก์แล้วเปิดอ่านเนื้อหา (ข้อ 1b) (2) หาส่วนต่างแล้วปรับ spec ให้ตรงไฟล์ — จุดที่ต่างจาก spec คือสิ่งที่ user แก้เอง ต้องรักษาไว้ (3) ถามสิ่งที่ยังค้างเป็นชุดเดียว (ข้อ 0) (4) เลือกวิธีแก้: ไม่เปลี่ยนโครง → แก้เฉพาะจุดบนไฟล์จริง (ข้อ 1c) · เปลี่ยนโครง → สร้างใหม่จาก spec (5) เขียนสคริปต์ลงดิสก์ (ข้อ 3) แล้วรันด้วยเครื่องหมายที่ตรงบทบาท: แก้ไม่เกินห้าจุดบนไฟล์ที่สมบูรณ์ใช้ `ICE_SMARTFIX=1` · นอกนั้นใช้ `ICE_BUILD=pipeline` พร้อม `ICE_BASE=` (งานนำเสนอ และงานทุกฟอร์แมตที่มีภาพ เพิ่ม `ICE_DESIGN=briefed`) (6) บันทึกรุ่นใหม่ (ชื่อไฟล์ `[ชื่อเอกสาร]_V##R##_YYYY.MM.DD.ext` ตาม `~/.claude/CLAUDE.md` PART 6) พร้อมย้ายรุ่นก่อนหน้าเข้า `_archive/` ซึ่งเป็นโฟลเดอร์ย่อยใต้โฟลเดอร์ผลงานเดียวกัน ในคำสั่งเดียวกัน แล้วส่งผู้ตรวจคุณภาพ

0. **ASK-FIRST ผ่านแล้ว** — ทุกข้อสงสัยที่ source ไม่ตอบ (ผู้อ่าน โครง ความยาว ตัวเลขที่ขาด สิ่งห้ามใส่ ภาษา ราง) ถูกถาม user เป็นชุดเดียวและได้คำตอบแล้ว · มีคำถามค้าง = ห้ามเริ่ม build · เจอกำกวมใหม่ระหว่าง build = หยุดถามทันที ห้ามเดา · เอกสารส่งมอบพร้อม "คำถามปรับปรุง" แนบท้าย = ทำผิดข้อนี้ (นิยามเต็ม: ไฟล์กัปตัน S1 · ไฟล์สมนึก T1)
1. **spec อยู่บนดิสก์แล้ว** — content-spec และ design-spec บันทึกเป็นไฟล์ตามแม่แบบ §0.5 ก่อนเสมอ · build อ่านจาก spec ไม่อ่านจากความจำใน context · เขียน spec ตามกติกาภาษาของสกิล `ice-writing-register` และทำ `_build/glossary.md` (ศัพท์ที่ลูกค้าใช้จริงพร้อมแหล่ง) ก่อนเขียน spec เพราะการแก้ถ้อยคำหลัง build เสร็จหมายถึง build ใหม่ทั้งรอบ (เคสจริงสิงหาคม 2026: user ต้องสอนเรื่องภาษาซ้ำห้าครั้งใน session เดียว)
1b. **DISK-IS-TRUTH — ไฟล์บนดิสก์คือความจริง ไม่ใช่ spec และไม่ใช่ความจำ** user แก้ไฟล์ผลงานด้วยตัวเองหลัง build เป็นเรื่องปกติ ก่อนแก้หรือ build ซ้ำต้องทำสามขั้นตามลำดับ: (1) `ls` หารุ่นสูงสุดบนดิสก์แล้วเปิดอ่านเนื้อหาจริง (ไฟล์ office ให้แตกอ่านเนื้อหา ไม่ใช่ดูแค่ชื่อ) (2) เทียบกับ spec หรือรุ่นที่ตัวเองเคยสร้าง หาจุดที่ user แก้ แล้วปรับ spec ให้ตรงไฟล์จริงก่อน (3) จึงเริ่มงาน และประกาศฐานด้วย `ICE_BASE=<path รุ่นที่ใช้เป็นฐาน>` หรือ `ICE_BASE=NEW` เมื่อสร้างครั้งแรก · ด่านตรวจก่อนสร้างไฟล์ (เฉพาะเส้นทาง `ICE_BUILD=pipeline`) เทียบลายนิ้วมือไฟล์กับรุ่นที่ build ล่าสุดให้เองด้วย ถ้าไฟล์ถูกแก้หลัง build จะปฏิเสธจนกว่าจะอ่านและรับการแก้เข้า spec แล้วประกาศ `ICE_ABSORBED=1`
   ❌ ผิด: นำ build script เดิมมารันสร้างรุ่นถัดไปโดยไม่เปิดไฟล์ปัจจุบัน — การแก้ด้วยมือของ user หายทั้งหมด (เคสจริง OCC: rebuild จากฐาน V42 ทั้งที่ดิสก์อยู่ที่ R57)
   ✅ ถูก: เปิดไฟล์รุ่นล่าสุด พบว่า user แก้หัวข้อหน้าห้าและตัวเลขหน้าเก้า บันทึกทั้งสองจุดเข้า spec แล้วจึงสร้างรุ่นใหม่ที่คงการแก้นั้นไว้
1c. **EDIT-IN-PLACE FIRST** — งานแก้ที่ไม่เปลี่ยนโครงสร้าง (ถ้อยคำ ตัวเลข สี ตำแหน่ง ขนาดตัวอักษร) ให้แก้เฉพาะจุดบนไฟล์รุ่นล่าสุดผ่าน API ของไลบรารีเอกสาร เพราะรักษาการแก้ของ user ไว้เองและใช้ทรัพยากรน้อยกว่ามาก · สร้างใหม่ทั้งไฟล์จาก spec เมื่อเปลี่ยนโครงสร้างเท่านั้น (เพิ่มลดหน้า เปลี่ยนลำดับ เปลี่ยนแม่แบบ) · เกณฑ์ตัวเลข: deck ใหม่หรือแก้เกิน 5 สไลด์ = build จาก spec · แก้ไม่เกิน 5 สไลด์บนฐานที่สมบูรณ์ = แก้ผ่าน API (การ rebuild จาก source คือการนำความเสียหายเดิมกลับมา) · เกณฑ์โครงสร้างมาก่อนเกณฑ์ตัวเลข: การเพิ่มหรือลบหน้า เปลี่ยนลำดับ หรือเปลี่ยนแม่แบบ ไม่นับเป็น "จุด" ของ `ICE_SMARTFIX=1` แม้จำนวนน้อย ต้อง build จาก spec ด้วย `ICE_BUILD=pipeline`
   ❌ ผิด: แก้ข้อความสองบรรทัดแล้ว build ใหม่ทั้งเล่ม (เคสจริง OCC: หนึ่งเอกสารสะสม 61 รุ่นด้วยวิธีนี้) · ✅ ถูก: เปิดไฟล์รุ่นล่าสุด แก้สองจุด บันทึกเป็นรุ่นถัดไป
2. **ประกาศโหมดใน PLAN-CARD แล้ว** (work_mode: lite หรือ full) และจัดคิว ⑤ อริสให้ตรวจไว้แล้ว
2b. **ตัวแปลภาษาที่ใช้ = `python3` ของระบบ** ซึ่งเป็นที่อยู่ของไลบรารีสร้างเอกสารทั้งสามตัว · ห้ามใช้ python ของ `_lib/.venv-doc` เพราะ venv นั้นมีไว้สำหรับเครื่องมืออ่านเอกสารคนละชุด · ไม่ต้องจำรายชื่อไลบรารี ให้ถามเครื่องมือ: `python3 ~/.claude/agents/_lib/env_check.py build` ตอบว่าใช้ตัวไหน มีอะไรแล้ว ขาดอะไร พร้อมคำสั่งติดตั้ง · เจอข้อความว่าไม่พบไลบรารีเมื่อไร ให้รันคำสั่งนี้ก่อนสรุปเสมอ แล้วทำตามคำสั่งติดตั้งที่มันพิมพ์ให้และรันงานซ้ำ
3. **เขียน build script ลงดิสก์** ที่ `_build/` (ไม่ใช่ heredoc ยาวใน context) แล้วรันด้วยเครื่องหมาย
4. **ฟอนต์มาจาก SSOT เท่านั้น ห้ามเขียนชื่อฟอนต์ตายตัวในโค้ด** — ใช้กับ build script ทุกตัวรวมที่เขียนมือรายโปรเจกต์:
   ```python
   import os, sys; sys.path.insert(0, os.path.expanduser("~/.claude/agents/_lib"))
   from font_policy import RAILS
   FONT = RAILS[rail]["font"]          # rail = "private" | "govt"
   ```
   เหตุผล (เคสจริง 2026.08.04): นโยบายล็อกแล้วแต่ `PWA TCO-Breakdown V01R22` ยังออกมาเป็น Sarabun และตัวตรวจขึ้นผ่าน เพราะ script เขียนมือตั้ง `FONT = "Sarabun"` เอง — สำรวจแล้ว 5 ใน 6 script ทำแบบเดียวกัน user เป็นคนจับได้ ไม่ใช่ระบบ
5. **จบ build ต้องผ่าน `audit_fonts.py` ก่อนคิว ⑤ อริส** (§6) — ผลนี้ได้มาสองทางโดยไม่ต้องรันเอง: build script ของทีม (`~/.claude/agents/_lib/build_pptx.py` · `build_docx.py` · `build_xlsx.py` · `build_dashboard.py` โฟลเดอร์เดียวกัน) เรียกให้ในตัว และหลังคำสั่งที่มีเครื่องหมายทุกคำสั่ง (รวม script เขียนเอง) `ice-postbuild-record.sh` รันให้กับไฟล์เอกสารที่เพิ่งถูกเขียนภายใน 2 นาที ในโฟลเดอร์ที่คำสั่งทำงานอยู่ (cwd) ลึกไม่เกิน 3 ชั้น ไม่รวม `_archive/` และ `_temp/` (ค้นจากเวลาแก้ไขไฟล์ ไฟล์ที่เขียนใน `_temp/` แล้วย้ายเข้าที่จริงในคำสั่งเดียวกันจึงยังถูกเห็น แต่ไฟล์ที่ค้างอยู่ใน `_temp/` ไม่ถูกตรวจ · พบหลายไฟล์ตรวจให้เฉพาะไฟล์แรก) แล้วแสดงผลในบริบท · ถ้า `_build/.last-built.json` ยังไม่มีหรือไม่มีชื่อไฟล์นั้น (build ครั้งแรก หรือ hook ไม่เห็นไฟล์) ด่านครั้งถัดไปข้ามการเทียบลายนิ้วมือ ไม่ปฏิเสธ — ความรับผิดชอบเรื่องอ่านไฟล์ล่าสุดจึงกลับมาอยู่ที่ขั้น 1b · ให้อ่านผลนั้น ห้ามรันซ้ำ (§6 SINGLE-PASS) · ต้องรันเองเฉพาะเมื่อผลอัตโนมัติไม่ครอบไฟล์ของท่าน (สร้างหลายไฟล์ในคำสั่งเดียว) แก้ไฟล์ด้วยมือนอกคำสั่งที่มีเครื่องหมาย หรือได้ไฟล์มาจากที่อื่น
6. **FILE HYGIENE** — ไฟล์ชั่วคราว ทดสอบ และ render ทุกชนิดไปที่เดียวของงานนั้น `<sub-project>/20-Output/_temp/` (หลักฐานตรวจใน `_temp/qa/`) · spec และ build script อยู่ `_build/` ข้างไฟล์ผลงาน · ไฟล์ผลงานจริงไปตำแหน่งที่ user หรือ spec ระบุเท่านั้น ไม่แน่ใจ = ถามก่อน · ห้ามสร้างไฟล์นอกโปรเจกต์โดยเฉพาะใต้ `~/Documents` · กติกาเต็ม `~/.claude/agents/reference/file-hygiene.md`
7. **iCE SUPER TEMPLATE** — เมื่อ user เอ่ยชื่อ "iCE Super Template" ให้ดึง `references/ice-super-template.md` มาใช้ทั้งชุดทันที (ปกเข้มไล่เฉดลายทองตามอุตสาหกรรม · โครง 6 หน้า · สูตรภาพพื้นหลัง Higgsfield ยิงครั้งเดียวต่อ deck · ชุดคำถามสั้น 4 ข้อ) · สั่ง deck ทั่วไปโดยไม่เอ่ยชื่อ = ห้ามเหมาใช้เอง ให้ถาม CI และแม่แบบตาม ASK-FIRST ปกติ · สี ขนาดตัวอักษร และกริด ยึด `~/.claude/skills/b2b-slide-designer/references/template_ice_propose.md` ห้ามแยกสำเนา · กฎออกแบบ 6 ข้อของ doctrine ยังใช้กับ deck นี้เหมือน deck อื่น
8. **โหลด skill ตามตารางเส้นทางก่อนคิด** — "งานประเภทไหนต้องโหลด skill ใดและเปิดไฟล์ใดก่อนเขียน spec" อยู่ที่ `~/.claude/hooks/skill-routing.yaml` เพียงแห่งเดียว ระบบอ่านตารางนั้นแล้วเติมคำสั่งโหลดเข้าบริบทให้เอง และด่านตรวจการเขียน spec กับด่านก่อนสร้างไฟล์จะปฏิเสธถ้ายังโหลดไม่ครบ (ข้อความปฏิเสธบอกชื่อ skill ที่ขาด ให้โหลดด้วย Skill tool แล้วรันซ้ำ) · เรื่องเดียวที่ต้องรู้เพิ่มจากที่นี่: เครื่องหมาย `ICE_DESIGN=briefed` ผูกกับฟอร์แมตผลลัพธ์และการมีภาพ ไม่ใช่กับ skill ที่ใช้วาด — ต้องประกาศใน (ก) ทุกคำสั่งสร้างหรือแก้ .pptx และ (ข) งานทุกฟอร์แมต (เอกสาร ภาพ หน้าเว็บ) ที่ต้องวาด infographic icon หรือแผนภาพ แม้ภาพนั้นวาดด้วย skill `diagram-design` (ตารางกรณีใช้ที่ §5.1) · สองกรณีที่ไม่ต้องประกาศ: .docx หรือ .xlsx ที่ไม่มีภาพเหล่านั้น และงานที่ส่งมอบเป็นไฟล์แผนภาพเดี่ยวซึ่งไม่มีเอกสารให้ตั้งโจทย์ · ด่านปฏิเสธอัตโนมัติเฉพาะ .pptx กรณี (ข) ผู้สร้างต้องถือเอง · การตั้งโจทย์ของ `diagram-design` กับ DESIGN BRIEF หัวข้อ 4.11 ไม่นับแทนกัน เพราะอันหนึ่งตัดสินภาพหนึ่งภาพ อีกอันตั้งโจทย์เอกสารทั้งฉบับ (บ้านของเครื่องหมายคือ `b2b-slide-designer` หัวข้อ 4.11.1)
9. **ไฟล์ PDF ประกอบ ต้องถามก่อนทำทุกครั้ง ห้ามทำเอง** — ไฟล์ Excel และ Word ฝังฟอนต์ไม่ได้ กติกาเดิมจึงให้ทำ PDF ส่งคู่ แต่ต้องถาม user ก่อนพร้อมวางทางเลือกทั้งสองบนโต๊ะ: "ไฟล์นี้ฝังแบบอักษรไม่ได้ ถ้าเปิดบนเครื่องที่ไม่มีแบบอักษรชุดเดียวกัน หน้าตาจะเพี้ยน ทางที่หนึ่ง ทำไฟล์ PDF ส่งคู่ไปด้วย แลกกับรอบตรวจที่เพิ่มขึ้นและรอยตัดกลางคำไทยในไฟล์แปลงซึ่งแก้ไม่ได้ ทางที่สอง ส่งไฟล์แบบอักษรให้ผู้รับติดตั้ง (`bash ~/.claude/agents/_lib/make_font_kit.sh "<โฟลเดอร์ผลงาน>"` สร้าง `_Fonts/` พร้อม README) ซึ่งแทบไม่มีต้นทุน ท่านเลือกทางไหน" · ยกเว้นไม่ต้องถามเมื่อ user สั่ง PDF ตรง ๆ หรือตอบไว้แล้วในรอบงานเดียวกัน · เหตุผล: งานเดือนกันยายน 2026 ระบบทำ PDF เอง 32 ครั้งโดยไม่มีใครสั่ง และปัญหาที่กินรอบตรวจมากที่สุด (รอยตัดกลางคำ 63 → 128 จุด) เกิดจากไฟล์ PDF ล้วน ๆ — การทำตามกติกาโดยไม่บอก user ว่ามีราคา คือความผิดพลาดเอง

| `ICE_SMARTFIX=1` | L1 | แก้ไม่เกิน 5 จุดบนฐานที่สมบูรณ์ · "จุด" = การแก้หนึ่งที่ที่แยกกันได้ (pptx นับสไลด์ · xlsx นับเซลล์หรือช่วงเซลล์ติดกัน · docx นับย่อหน้าหรือตาราง) · เกิน 5 = build ใหม่ · ด่านปล่อยเส้นทางนี้ผ่านทันทีโดยไม่ตรวจ `ICE_BASE` `ICE_DESIGN` หรือ skill ที่โหลด แต่ขั้น 1b (อ่านไฟล์รุ่นล่าสุดก่อน) ยังบังคับเหมือนเดิม เพราะการแก้บนไฟล์จริงคือการอ่านไฟล์นั้นอยู่แล้ว (ขั้น 1b ที่บังคับคือขั้น (1) อ่านไฟล์จริงและ (2) ปรับ spec · ขั้น (3) ประกาศ `ICE_BASE` ใส่ได้แต่ด่านไม่ตรวจ) · PLAN-CARD ของงานแก้เล็กแสดงเพียงรายการจุดที่จะแก้ `work_mode` และคิว ⑤ ไม่ต้องตาราง action_title ทั้งชุด · เส้นทางนี้ด่านไม่เทียบลายนิ้วมือ จึงไม่ต้องประกาศ `ICE_ABSORBED=1` และไม่ต้องประกาศ `ICE_DESIGN=briefed` ซ้ำเพราะฐานผ่าน DESIGN BRIEF มาแล้ว (ฐานที่ไม่เคยผ่าน brief เช่น deck เก่าก่อนมีกฎ 4.11 หรือไฟล์ที่ลูกค้าส่งมา = กำกวม ให้ถาม user ก่อนว่าจะแก้เฉพาะจุดโดยคงดีไซน์เดิม หรือทำ brief แล้ว build ใหม่) — แต่ถ้าการแก้เพิ่มภาพ infographic หรือ icon ใหม่ ต้องตั้งโจทย์ภาพนั้นตามหัวข้อ 4.11 เองแม้ด่านไม่ตรวจ · หลัง build hook ยังบันทึกลายนิ้วมือและรันตัวตรวจให้ตามปกติ · deck ที่ฝังฟอนต์ไว้แล้ว หลังแก้ต้องรัน `validate_pptx_fonts.py` กับไฟล์ที่บันทึกใหม่ (ตารางท้ายไฟล์แถว 4) ถ้าไม่ผ่าน ให้ฝังซ้ำด้วย Method B ก่อนส่ง |
| `ICE_INLINE_APPROVED=1` | ตาม FAILURE PROTOCOL ของไฟล์กัปตัน | user อนุมัติข้อยกเว้นแล้ว |
| `ICE_BASE=<path>` หรือ `ICE_BASE=NEW` | ทุกคนที่ build ด้วย `ICE_BUILD=pipeline` (ด่านตรวจเครื่องหมายนี้เฉพาะเส้นทางนั้น) | ประกาศฐานที่ใช้สร้างรุ่นนี้ · ถูกปฏิเสธว่า "ไม่มีเครื่องหมาย" = ยังไม่ได้อ่านไฟล์รุ่นล่าสุด ให้ `ls` โฟลเดอร์ผลงาน เปิดอ่านรุ่นสูงสุด แล้วประกาศ path นั้น (§0.1 ข้อ 1b) · ถูกปฏิเสธว่า "ไม่ใช่รุ่นล่าสุด" = ข้อความบอกชื่อไฟล์ที่ใหม่กว่า ให้อ่านรุ่นนั้นแล้วประกาศใหม่ · ไฟล์วัตถุดิบที่ลูกค้าส่งมาไม่ใช่ฐาน ให้ใช้ `NEW` |
| `ICE_DESIGN=briefed` | ทุกคำสั่ง .pptx และงานทุกฟอร์แมตที่มี infographic icon หรือแผนภาพ (ขอบเขตเต็ม §0.1 ข้อ 8) ยกเว้นเส้นทาง `ICE_SMARTFIX=1` ตามแถวบน | ยืนยันว่าทำ DESIGN BRIEF ตาม `b2b-slide-designer` หัวข้อ 4.11 แล้ว · ด่านปฏิเสธอัตโนมัติเฉพาะ .pptx · deck ที่ผ่าน brief แล้วและ build ซ้ำเพื่อเพิ่มหน้า ไม่ต้องทำ brief ทั้งฉบับใหม่ ให้เติมเลย์เอาต์ ภาพ และ icon ของหน้าใหม่ลง design-spec แล้วประกาศเครื่องหมายได้ · ทำ brief ใหม่ทั้งฉบับเมื่อเปลี่ยนแม่แบบหรือชุดสี · ถูกปฏิเสธ = เปิดหัวข้อ 4.11 ตอบชุดคำถาม เขียนผลลง design-spec แล้วรันซ้ำ (บ้านของเครื่องหมายคือหัวข้อ 4.11.1 ของสกิลนั้น) |
| `ICE_ABSORBED=1` | ผู้ที่ build ต่อจากไฟล์ที่ user แก้เอง | ยืนยันว่าอ่านไฟล์ที่ user แก้ หาส่วนต่างครบ และปรับ spec ให้ตรงแล้ว · ใช้เมื่อไฟล์ฐานถูกแก้หลัง build ล่าสุด (§0.1 ข้อ 1b) — ประกาศได้ตั้งแต่คำสั่งแรกทันทีที่ทำขั้น 1b ครบ ไม่ต้องรอให้ด่านปฏิเสธก่อน เพราะด่านดูเพียงว่ามีเครื่องหมายหรือไม่ (รู้ล่วงหน้าได้จาก user บอกว่าแก้เอง หรือจากวันที่ไฟล์ใหม่กว่า `_build/.last-built.json`) |
| `ICE_RAIL=<private\|govt>` | ผู้ที่ใช้ `build_deck.py` `build_html.py` หรือ `build_dashboard.py` | ไม่ใช่เครื่องหมายที่ด่านตรวจ แต่เป็นตัวแปรสภาพแวดล้อมที่สามสคริปต์นั้นอ่านเพื่อเลือกราง (§3.0) ไม่ใส่ = `private` · `build_pptx.py` `build_docx.py` และ `build_xlsx.py` ไม่อ่านตัวแปรนี้ แต่หารางด้วย `font_policy.infer_rail` ตามลำดับ: ช่อง `rail` ใน spec → ช่อง `doc_type` → คำบ่งงานราชการในชื่อไฟล์หรือหัวเรื่อง → ไม่มีสัญญาณ = `private` พร้อมพิมพ์เหตุผลบอก · งานราชการจึงควรเขียน `rail: govt` ใน spec ตรง ๆ · ค่าต้องตรงกับ `--rail` ตอนตรวจ |

ป้าย L0 และ L1 ในช่อง "ใคร" คือผู้ build คนเดียวกันตามนิยาม 0.0 (L0 สวมบท L1) แยกไว้ตามที่มาของเครื่องหมาย ไม่ใช่การแบ่งงาน · ทุกคำสั่ง Bash ที่รัน python สร้างหรือแก้ .pptx .docx .xlsx ต้องขึ้นต้นด้วยเครื่องหมายที่ตรงบทบาท ไม่มี = ด่านปฏิเสธโดยตั้งใจ · การอ่านหรือตรวจไฟล์ไม่ถูกปิดกั้น · เครื่องหมายไม่ใช่ของแจก ห้ามใส่ให้ context อื่นที่ไม่ได้โหลดสกิลนี้ · ด่านยังตรวจด้วยว่า session โหลด skill ตามตารางเส้นทางครบหรือยัง (§0.1 ข้อ 8) · หลัง build สำเร็จ `~/.claude/hooks/ice-postbuild-record.sh` บันทึกลายนิ้วมือไฟล์ลง `_build/.last-built.json` และรันตัวตรวจฟอนต์ เลย์เอาต์ และภาษาให้อัตโนมัติ ผลปรากฏในบริบททันที

**แม่แบบ .pptx จริง (`ICE_TEMPLATE=<path>` — ตัวแปร ไม่ใช่เครื่องหมายของด่าน):** ตั้งแต่ 2026.09.05 มีแม่แบบ `~/.claude/skills/b2b-slide-designer/assets/masters/iCE-Propose_Master.pptx` (16:9 · theme font ทั้งสามช่องเป็นฟอนต์รางเอกชน · สีจาก tokens ของ iCE · layout 10 แบบ: cover · divider · action-title-body · two-column · three-card · table · timeline · closing · appendix · blank) · `build_pptx.py` และ `build_deck.py` เปิดแม่แบบนี้เมื่อตั้งตัวแปร แล้วเติมเนื้อหาลง placeholder แทนการวาดจาก shape เปล่า (shape ต่อหน้าลดจากราว 47 เหลือราว 7) · ชื่อ layout และ idx ของ placeholder อยู่ที่ `…/assets/masters/README.md` · สถานะ: user ยังไม่อนุมัติหน้าตาแม่แบบจากภาพใน `…/assets/masters/_review/` ด่านก่อนสร้างจึงยังไม่บังคับตัวแปรนี้ ใช้ได้เมื่อ user สั่งหรืออนุมัติแล้ว

## 0.3 SAVE-FIRST · NO SELF-RENDER

## 0.5 แม่แบบ content-spec รายหน้า (คำสั่ง user 2026.09.05 — ชุดช่องเดียวกับ `b2b-presentation-creator` ขั้นที่ 6 และ doctrine ข้อ 4-5)

content-spec คือต้นทางของทั้งการสร้างและการตรวจ จึงต้องมีช่องครบทุกหน้า ตัวตรวจอัตโนมัติ (`audit_layout.py`) และอริสอ่านค่าจากช่องเหล่านี้ · ประกาศครั้งเดียวต่อชุด: `mode` (`presenter` หรือ `document`) และ `palette_base` (Corporate Identity ของลูกค้า หรือชื่อชุดสีจากคลัง `~/.claude/skills/b2b-slide-designer/references/catalog-gradients.md` ห้ามคิดสีเอง — ถ้าคู่มือ CI ห้ามไล่เฉดให้บันทึกเหตุผลไว้ในช่องนี้)

| ช่อง (ทุกหน้า) | ใส่อะไร | ถ้าไม่มีข้อมูล |
|---|---|---|
| `objective` | หน้านี้ทำให้ผู้ฟังตัดสินใจอะไร — ใช้ตอนคิดเท่านั้น ห้ามขึ้นสไลด์ เพราะกลายเป็นการบรรยาย | หน้าที่ตอบไม่ได้ว่าให้ผู้ฟังตัดสินใจอะไร = ไม่ควรมีหน้านั้น |
| `action_title` | ประโยคสรุปที่เป็นหัวเรื่อง ยาวไม่เกินสองบรรทัด (ไม่ใช่ชื่อหัวข้อ) | เขียนใหม่จนเป็นประโยคที่มีกริยาหรือการเปรียบเทียบ |
| `key_message` | ใจความของหน้า ไม่เกินงบคำของโหมด: presenter 25 คำ · document 75 คำ (นับทุกกล่องรวม action title และป้ายในภาพ ไม่รวมส่วนท้ายหน้า · ไทยนับด้วยการตัดคำ 4.5 ตัวอักษรต่อคำ · ป้ายที่ฝังอยู่ในไฟล์ภาพ เช่น PNG จาก diagram-design ตัวตรวจอ่านไม่ได้ ผู้เขียน spec นับรวมเองตอนกำหนด key_message) | เกินงบ = แตกเป็น bullet หรือแยกหน้า |
| `evidence` | ตัวเลข ข้อเท็จจริง หรือแหล่งที่มาที่รองรับใจความ | เขียน `[NEED FROM USER: …]` แล้วรวบไว้ในรายการสิ่งที่ต้องได้จาก user — ห้ามกุ (H3) |
| `visual` | ภาพประกอบ แผนภาพ หรือ infographic ของหน้านี้ และ icon ที่ใช้ (เลือกจากคลังก่อนวาดใหม่) — หน้าเนื้อหาทุกหน้าต้องมี ยกเว้นปก หน้าคั่น หน้าปิด | หน้าเนื้อหาที่ไม่มีภาพ = ตัวตรวจไม่ผ่าน |
| `topic_id` | รหัสเรื่องของหน้า — หน้าที่ใช้ชุดความหมายเดียวกันในการระบายสี (legend เหมือนกัน) ใช้รหัสเดียวกัน | ผู้ออกแบบกำหนดตอนเขียน spec |
| `color_set` | ชุดสีที่หน้านี้ใช้ ต้องตรงกันทุกหน้าที่มี `topic_id` เดียวกัน และหน้าที่ไม่เกี่ยวห้ามแสดง legend ของชุดนั้น | ไม่มีสีสื่อความหมาย = ระบุ `none` |

ตัวอย่างหนึ่งหน้าใน content-spec:
```yaml
mode: document            # ครั้งเดียวทั้งไฟล์
palette_base: "CI ลูกค้า: น้ำเงิน #0A3D62 ไล่เฉดตามคู่มือ CI ปี 2025"
pages:
  - no: 5
    objective: ให้ CFO เห็นว่าปิดงบช้าเพราะกระทบยอด 3 จุด ไม่ใช่เพราะคน
    action_title: ปิดงบ 12 วันมาจากงานกระทบยอด 3 จุดที่ยังทำด้วยมือ
    key_message: กระทบยอดธนาคาร เจ้าหนี้ และสินทรัพย์ถาวรใช้ 9 ใน 12 วัน ทั้งสามจุดมีระบบรองรับอยู่แล้ว
    evidence: "[NEED FROM USER: จำนวนวันจริงของแต่ละจุดจากรายงานปิดงบไตรมาสล่าสุด]"
    visual: แผนภาพเส้นเวลา 12 วัน แบ่งสีตามงาน 3 จุด + icon ธนาคาร ใบแจ้งหนี้ อาคาร
    topic_id: closing-steps
    color_set: gradient-blue-3
```
งาน .docx และ .xlsx ใช้ spec รูปแบบเดิม (โครงเอกสารรายหัวข้อหรือราย sheet พร้อม `rail` และ `key_facts`) แต่หน้าหรือ sheet ใดที่มีภาพหรือสีสื่อความหมาย ให้ใส่ช่อง `visual` `topic_id` `color_set` ของหน้านั้นด้วยกติกาเดียวกัน · design-spec ของไฟล์นำเสนอบันทึกผลของ DESIGN BRIEF (แม่แบบ เลย์เอาต์รายหน้า ชุด icon `font_strategy`) · design-spec ของ .docx และ .xlsx ที่ไม่มีภาพคือข้อกำหนดรูปแบบ (ราง ฟอนต์ ขนาด ความกว้างคอลัมน์ ชื่อ style) ไม่ต้องทำ DESIGN BRIEF 4.11 และเขียนรวมอยู่ในไฟล์ content-spec เดียวกันได้ เพราะด่านตรวจการเขียน spec ดูที่ชื่อไฟล์ ไม่บังคับให้แยกสองไฟล์ · แนบ PLAN-CARD ให้ user เห็นตาราง action_title ทั้งชุด (หรือโครงหัวข้อและ sheet) ก่อน build

## 3.1 DOCX — วินัยฟอนต์ W1-W3 และวินัยตาราง W4-W5

**คืออะไร:** กฎ 5 ข้อของไฟล์ Word — **W1** ตั้ง `w:ascii` `w:hAnsi` `w:cs` เป็นฟอนต์ตัวเดียวกัน (สเปก Microsoft สองฉบับขัดกันเองว่าไทยใช้ช่องไหน · ไม่ตั้ง `w:cs` → Word ถอยไป Times New Roman แล้วแทนด้วย Angsana เงียบ ๆ) และตั้งที่ราก `styles.xml` (docDefaults · Normal · Heading · Table) ไม่ไล่แก้ราย run · **W2** `w:bCs` และ `w:iCs` ทุกครั้งที่มี `w:b` `w:i` (ไม่งั้นหัวข้อไทยไม่หนาแต่อังกฤษหนา) · **W3** ห้าม `lineRule="exact"` ในย่อหน้าที่มีไทย (วรรณยุกต์ถูกตัด) · **W4** ทุกตารางตั้งแต่ 2 คอลัมน์ต้องตั้ง `w:tblLayout` เป็น fixed พร้อมเขียน `w:tblGrid` ใหม่และตั้ง `w:tcW` ทุกช่องในรอบเดียว ไม่งั้นตัวจัดหน้าเฉลี่ยทุกคอลัมน์เท่ากันโดยทิ้งค่าที่ตั้งไว้ (เคสจริง OCC: ตั้ง 1.4/5.0/7.0/3.0 ซม. ได้ 4.2 ซม. เท่ากันทุกคอลัมน์) และเมื่อความกว้างไม่พอห้ามไล่แก้ทีละคอลัมน์ ให้วัดความกว้างขั้นต่ำของทุกคอลัมน์พร้อมกันจากไฟล์ฟอนต์จริงแล้วตั้งครั้งเดียว ไม่พอ = ปัญหาเนื้อหา เสนอ user แก้ข้อความ (เคส TQR วน 5 รุ่น) · **W5** แถวเนื้อหาทุกแถวตั้ง `w:cantSplit` ไม่งั้นแถวขาดกลางหน้า · ขนาด `w:szCs` ต้องเท่า `w:sz` เมื่อใช้ฟอนต์ตัวเดียว · ลบ theme attribute (`w:cstheme` ฯลฯ) ออกจาก styles และ run · ห้ามฝัง odttf ด้วยมือ (Word ปฏิเสธ) · .docx ที่ส่งลูกค้า ฝังฟอนต์ไม่ได้จึงต้องเสนอทางเลือกตาม §0.1 ข้อ 9 (PDF companion หรือชุดฟอนต์) โดยถาม user ก่อนเสมอ ไม่แนบ PDF เอง · user สั่งว่า "ส่ง .docx อย่างเดียว" นับเป็นคำตอบแล้ว ไม่ต้องถามซ้ำ
**ใช้เมื่อ:** เขียน build script ของ Word · ผลตรวจฟ้อง FAIL W1 W4 W5 · เอกสาร Word ตารางเพี้ยนหรือแถวขาด · **อยู่ที่** `references/docx-discipline.md` ส่วนที่ 1 (เหตุผล เคสจริง โค้ดที่พิสูจน์แล้ว และรายการ VALIDATOR DOCX)
**ด่านตรวจ:** `python3 ~/.claude/agents/_lib/audit_fonts.py --rail <private|govt> FILE.docx` ตรวจ W1 W4 W5 และด่านฟอนต์ V1 V2 V4 ให้ · W2 W3 และเกณฑ์ `szCs` ไม่มีด่านอัตโนมัติ ผู้ build ต้องถือเอง (เครื่องจับไม่ได้ไม่ได้แปลว่าได้รับยกเว้น) · ด่านตอบ "กฎถูกปฏิบัติตามหรือไม่" ส่วน "เกิดความเสียหายจริงหรือยัง" (แถวขาดกลางหน้าจริงไหม) ตอบได้จาก render ซึ่งเป็นหน้าที่ ⑤ อริส และความไม่แน่นอนของคำถามหลังห้ามนำมาลดระดับการตรวจคำถามแรก

## 3.2 XLSX — E1-E6

**คืออะไร:** Excel ยากที่สุดเพราะเซลล์มีฟอนต์ได้ชื่อเดียว ไม่มีช่องไทยแยก · ฝังฟอนต์ไม่ได้ · ไม่มีสูตรทางการว่าฟอนต์ขนาดหนึ่งต้องใช้แถวสูงเท่าไร — กฎ 6 ข้อ: **E1** ฝังฟอนต์ไม่ได้ทุกแพลตฟอร์ม → งานส่งลูกค้าใช้บันได §3.0-A (แจกฟอนต์หรือ PDF companion ตาม §0.1 ข้อ 9) · **E2** ความสูงแถวต้องพอกับข้อความจริง ตัดสินที่ผลลัพธ์ — ค่าเริ่มต้นคือปล่อย auto-height (ไม่ตั้ง `customHeight`) เพราะการเดาจำนวนบรรทัดหลัง wrap คือสิ่งที่พลาด ตั้งเองได้เฉพาะแถว merge ที่ไม่มีไทย wrap · แถว banner · หรืองานที่ต้องแบ่งหน้าตรงกันทุกเครื่อง โดยใช้พื้น pt × 1.72 × บรรทัดที่รู้แน่ + 6 (เคสจริง CP Axtra: สูตร ×1.45 เฉือน 83/112 แถว · auto เฉือน 0/140 · ยืนยันกับ Excel จริงแล้ว) · **E3** vertical = center ทุกเซลล์ที่มีไทย (ค่าเริ่มต้น bottom ตัดวรรณยุกต์ด้านบน) · **E4** ห้าม merge cell ในแถวที่มีไทย + wrap (AutoFit ถูกปิดในแถว merge) ใช้ Center Across Selection แทน · **E5** ห้าม Shrink to fit กับเซลล์ไทย · **E6** ตั้ง default font ของ workbook ก่อนคำนวณความกว้างคอลัมน์ (หนึ่งหน่วยความกว้าง = ความกว้างเลข 0 ของฟอนต์ Normal) · ทำผ่าน NamedStyle ไม่ตั้งราย cell · `theme1.xml` ตั้งเป็นฟอนต์ราง
**ใช้เมื่อ:** เขียน build script ของ Excel · ผลตรวจฟ้อง FAIL E2-E5 · ข้อความในเซลล์ถูกเฉือน · **อยู่ที่** `references/xlsx-discipline.md` ส่วนที่ 1 (ตัวเลขที่วัดจริง กรณีตั้งเอง 3 กรณี และเหตุผลที่สูตรเก่าผิด)
**ด่านตรวจ 2 ชั้น:** ① สถิต `python3 ~/.claude/agents/_lib/audit_fonts.py --rail <ราง> FILE.xlsx` (FAIL E2 เฉพาะแถวที่ตั้งเองแล้วสั้นกว่าหนึ่งบรรทัดตาม metric ฟอนต์จริง · บอกไม่ได้ว่าข้อความ wrap ถูกเฉือนไหม) ② ผลจริง บังคับสำหรับงานส่งลูกค้าทุกขนาด: `python3 ~/.claude/agents/_lib/xlsx_rowheight_probe.py FILE.xlsx` ให้ LibreOffice จริงคำนวณ auto-height แล้วเทียบกับที่ตั้งไว้ (exit 3 = พบแถวไม่พอ พร้อมค่าที่ต้องการ · แก้แล้วรันซ้ำจน exit 0 ภายใต้เพดาน 2 รอบของ §6 ข้อ 2 ถึงเพดานแล้วยังไม่ผ่านให้หยุดรายงาน) แล้วดูภาพจริงด้วย `bash ~/.claude/agents/_lib/render_pdf.sh FILE.xlsx OUTDIR --expect "<ชื่อฟอนต์ตามที่ปรากฏใน PDF>" --strict-fonts` (§7) ซึ่งเป็นด่านเดียวที่ตอบเรื่องการเฉือนได้ ตัวตรวจเขียวไม่ใช่หลักฐานว่าข้อความครบ · ผู้ทำแต่ละส่วน: probe ผู้ build รันเองได้เพราะคืนตัวเลขไม่ใช่ภาพ · การ render ดูภาพเป็นของ ⑤ อริสในรอบตรวจตาม §0.3 (ผู้ build render เองเฉพาะสองข้อยกเว้นของ §0.3)

# §7 — RENDERER LADDER (ใช้เมื่อถูกสั่ง preview หรือเมื่อ ⑤ ต้อง render — พิสูจน์บนเครื่องนี้ VFIN 2026.07.17)

**กฎข้อ 0 (บทเรียน Akara 2026.08.01): ห้ามเรียก `soffice` เปล่า ๆ จาก PATH** เพราะบนเครื่องนี้ `which soffice` ชี้ไป shim ของ codex runtime ซึ่งมองไม่เห็น `/Library/Fonts` แล้วแทนฟอนต์ทั้งไฟล์โดยรายงานว่าสำเร็จ (ทดสอบไฟล์เดียวกัน: shim ให้ NotoSans FrankRuhlHofshi LinuxLibertineG · ตัวจริงให้ IBMPlexSansThaiLooped) · ผลตรวจจาก renderer ผิดตัวคือหลักฐานปลอม ทีมเคยไล่แก้ layout ที่ไม่ได้พังทั้งรอบ

ใช้ helper เสมอ เพราะหา binary ตัวจริงและตรวจฟอนต์หลัง render ให้ในตัว:
```bash
bash ~/.claude/agents/_lib/render_pdf.sh <ไฟล์> [outdir] --expect "<ชื่อตระกูลตามที่ปรากฏใน PDF>" --strict-fonts [--allow "<ฟอนต์ที่ตั้งใจใช้เพิ่ม>"]
bash ~/.claude/agents/_lib/render_pdf.sh --which        # ดูว่าเครื่องนี้จะใช้ตัวไหน
```
งานส่งลูกค้าทุกฟอร์แมตใส่ `--strict-fonts` เสมอ ให้ "ฟอนต์แปลกปน" เป็นความล้มเหลว (exit 8) ไม่ใช่คำเตือน · ชื่อใน `--expect` คือชื่อที่ปรากฏใน PDF (เช่น `IBMPlexSansThaiLooped`) ยังไม่รู้ให้ render เปล่าหนึ่งครั้งแล้วอ่านจากตารางที่ helper พิมพ์ · รหัสจบ: 0 ผ่าน · 2 เรียกผิดหรือไม่พบไฟล์ · 3 ไม่พบ LibreOffice ตัวจริง · 4 render ไม่ได้ไฟล์ · 5 ฟอนต์ไม่ฝังหรืออ่าน PDF ไม่ได้ · 6 เจอฟอนต์ fallback ของ Linux (renderer ผิดตัว) · 7 ไม่พบฟอนต์ที่คาด · 8 ฟอนต์ปนแบบ strict

บันได: ① LibreOffice ด้วย path เต็ม `/Applications/LibreOffice.app/Contents/MacOS/soffice --headless -env:UserInstallation=file:///tmp/lo-run --convert-to pdf` (ไม่ใส่ profile ใหม่ = พิมพ์ convert แต่ไม่เขียนไฟล์ · `--version` ต้องขึ้นต้น "LibreOffice ") ② PowerPoint AppleScript save-as-PDF ความเที่ยงสูงสุด — ปลายทางต้องเป็น POSIX file · sandbox เขียน `/private/tmp` ไม่ได้ จึงใช้ staging `~/Documents/.ice-staging/` แล้วย้ายเข้า `<sub-project>/20-Output/_temp/` ในคำสั่งเดียวกัน (`osascript … && mv … && rmdir`) เพราะการทำครึ่งแรกแล้วลืมครึ่งหลังคือต้นตอขยะใต้ `~/Documents` ที่ user เจอ ③ PowerPoint MCP ใช้เช็คแค่ "เปิดได้ ไม่ขึ้น Repair" (export_pdf เป็น false success ห้ามใช้ render) ④ ไม่มีทางไหนได้ = บอกตรง ๆ ว่ายืนยันบนเครื่องนี้ไม่ได้ ห้ามหลุดไปวนสอบสวน

# §8 — CODEX / OPENROUTER เป็นที่ปรึกษาทางเลือก

ผู้ build ใช้ Codex หรือ OpenRouter เป็นที่ปรึกษาทางเลือกได้ตาม codex_scope ที่ user เปิด (review โค้ด build ก่อนรันงานใหญ่ · ภาษาในไฟล์ก่อนส่ง ⑤ · ไอเดียออกแบบ) · ผู้ตรวจภายนอกว่าผ่าน ≠ ข้าม STRICT VALIDATOR และ γ1 ของตัวเอง ต้องรันเสมอ (เสริม ไม่แทน) และการตรวจจริงยังเป็นอริส · L0 เรียกเองใน loop หลักเสถียรกว่าให้ subagent เรียก · เจนนี่ตั้ง `codex_scope: none` เสมอ · วิธีเรียกอยู่ที่สกิล `claude-codex-bridge` และ `openrouter-bridge`
